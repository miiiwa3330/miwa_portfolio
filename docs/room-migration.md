# 部屋の中への移行 — 要件と設計

トップページの3Dを「ボクセルの惑星を外から回って見る」から「**ロケットのコロニーの中にある自分の部屋を、内側から見渡す**」へ作り替えるための要件定義と設計。ブランチは `feature/room-world`（2026-10-01 に `main` の `bf2bef8` から切った）。

前回の移行の記録 [planet-migration.md](planet-migration.md) と同じく、要件→設計→各手順の結果の順に書き足していく。完了したら題に「— 完了済み」を付け、現在の構造は `tech.md` と `scene-invariants.md` へ移す。

**経緯**: 世界観は 9/15 に「惑星をやめて衛星（ステーション）へ」と決まり（[devlog 2026-09-15](devlog/202609.md#2026-09-15)）、翌 9/16 未明の会話で「外から見る」から「内側から見渡す」へ、さらに「自分の部屋」へと進んでユーザーが「その方向で行きます」と決めた。**この 9/16 の決定は devlog に書かれないまま**で、10/01 に会話ログから見つけ直した（[devlog 2026-10-01](devlog/202610.md#2026-10-01)）。`sandbox/station-draft*.html` は外から見る案の頃の試作で、この移行の設計の根拠には使わない。

                   PC（正面・ホーム）   ホログラム（自己紹介）
   通信端末・扉                                   展示棚

   調査ボード                                     技術書の本棚

- **並び（ユーザー承認）**: PC → ホログラム（自己紹介）→ 展示棚（制作実績）→ 本棚（スキル）→ 調査ボード（経歴・活動）→ 通信端末（連絡先）→ PC。**PCの右隣から、今のヘッダーのナビと同じ順**なので、ナビで飛んでも部屋の中の位置関係と矛盾しない
- **扉と丸窓を置く**（ユーザー）。扉は通信端末の脇（連絡先＝外とつながる場所）。丸窓はコロニーの縦穴を覗く窓（9/16 の案）
- **ハンモックを置く**（ユーザー）。セクションではない、生活の物。巡回の途中で何も起きない区間になるが、「自分の部屋」らしさを出す
- 調査ボードは横に長いので、ほかの物より広い角度を取る
- **扉から机までの区間に、作業台（3Dプリンタ）を置く**（ユーザー）。`reference/4/1.png` で何も無かった区間を埋める。展示棚に並ぶ物を「ここで作っている」という物語にもなる
- **丸窓とハンモックは、本棚と調査ボードの間（PC の真後ろ）。** 丸窓の下にハンモックを吊るし、寝転んで窓の外を眺める場所にする。セクションではない区間を1か所にまとめる（Claude 案。この配置で生成した `reference/4/1.png` をユーザーが「いい感じ」と評価）

### 決まっていないこと


- **PCのGUIの作り方。** 3Dオブジェクトとして存在させる方法は2つある:
  - **HTML を3D空間に置く**（`drei` の `<Html transform>`。CSS の3D変換で、モニターの面に HTML の要素を貼る）。見た目は部屋の中の物のまま、文字は本物の HTML なので検索・スクリーンリーダー・文字の選択が効く。**こちらを第一候補にする**
  - **画面をテクスチャに描く**（canvas に描いた絵をモニターの面に貼る）。3Dとしては素直だが、中身が絵になるので検索にも読まれない。AdSense で「有用性の低いコンテンツ」と判定された経緯（2026-09-19）があり、読める中身を絵に置き換える方向には動かせないので採らない
  - HTML を3Dに置く方式で確かめること: **手前の3Dの物に隠れるか**（DOM は canvas の外にあるので、そのままでは3Dの物の手前に出る。`drei` の `occlude` で足りるか）、**透明な canvas の3層構成**（`scene-invariants.md` の「React / R3F の境界」）との重なり順、PCの画面の中の操作とカメラのドラッグの取り合い（`pointerClaim` と同じ問題）
- **PCの中身と詳細ページ（シート）の関係。** 5区画を押したときは今の詳細ページが開く想定なので、同じ情報がシートとPCの2か所に出る。**データと部品は1つにして両方から使う**（「同じ数を2箇所に持たない」）。ノートのように別のページへ移るものを、PCの中でどう扱うかも決める
- **PCが正面のあいだ、カードの場所が空くこと。** PC はカードを出さないので、PC では画面左のカード（スマホでは下のカードレール）が消える。スマホのレールは「3枚の窓」として組んであり（`scene-invariants.md` の「スマホ」節）、6か所中1か所だけ窓が空になる扱いを決める
- **展示棚の品をボクセルにするか。**
- **左のモニターに流す動画の中身。** 素材が要るので、`public/` に置くファイルの大きさ（配信サイズ）も一緒に決める
- **自分自身の見た目。** 監視カメラ・下を向いたときの体・手・映り込みの4か所で同じ姿に見える必要がある。ボクセルか、部屋と同じ作りか、シルエットかは未定
- **自分自身の描画の重さ。** 監視カメラと映り込みは、どちらも「別のカメラから部屋をもう一度描く」ことになる（樽型の魚眼と同じ種類の代償）。監視カメラは毎フレームでなく間引いて描く、映り込みは本物の反射ではなく薄い絵で済ませる、などを設計で決める。視点のカメラは自分の頭の中にあるので、頭は視点のカメラにだけ描かない（three.js のレイヤーで出し分ける）
- **樽型の魚眼が実機で重くないか。** 方式は決まった（立体射影・161°）が、魚眼の段は1フレームに部屋を6回描く。スマホも含めて実機で確かめる
- **ホログラムの文字の流し方。** 今のクロール（`reference/2/image9.jpg` に合わせた奥へ流れる列、自動再生、読み終えたらホームへ戻る）をどこまで引き継ぐか。今の自己紹介はシートを持たない唯一のセクションで、「読み終えること」が帰り道になっている（`tech.md` の「自己紹介の帰り道は『読み終えること』」）
- **照明の細部。** ネオンの色の組み合わせをいくつ用意するか（今はシアンと琥珀）、部屋のスイッチをどこに付けるか、画面のボタンをどこに置くか。**照明の状態は1か所に持ち、部屋のスイッチと画面のボタンはどちらもそれを書き換えるだけにする**（「同じ数を2箇所に持たない」）。部屋のスイッチは3Dの物なので、空タップの停止と混ざらないよう `pointerClaim` で名乗る（今の太陽と同じ）
- **参考写真。** CLAUDE.md の「値は参考写真・実測から導く」に従うには、部屋の構図の参考が要る。`reference/3`（旧 `reference/now`）の12枚は外観・街路・通路が中心で、個人の部屋の写真は無い。10/01 に生成画像2枚を `reference/4` に置いた（下の「参考画像」）。構図・雰囲気の参考にはなるが、生成画像なので寸法を導く根拠にできるかは、使う場面ごとに判断する

### 魚眼の2案

| | 画角を広げるだけ | 魚眼レンズ風の歪み |
| --- | --- | --- |
| 見え方 | 視野角を広げる（今の `CAMERA_FOV` は 45°）。画面の端の物ほど引き伸ばされる | 中央が膨らみ、端が丸く曲がる。広く写しても端が引き伸ばされない |
| 実装 | カメラの値1つ。軽い | 画面全体を描き直す処理（ポストプロセス）が要る |
| 既存の仕組みとの関係 | マーカーの画面上の位置・大きさの計算（`markerScreen`・`pixelsPerWorldUnit`）はそのまま成り立つ | **画面上の位置がレンズの式でずれるので、カードからマーカーへの点線の射影も同じ式で曲げる必要がある。** また、自己紹介の文字より3Dを手前に出す仕組みは canvas の透明に依存していて、ポストプロセスがアルファを塗りつぶすと壊れる（ネオンのブルームと同じリスク） |

## 試作 `sandbox/room-lab.html` の結果（10/01、ヘッドレスで確認）

円形の部屋（半径4.5m、壁の高さ3.4m、目の高さ1.6m）に要件の物を仮の形で置き、中央から見回す試作。**魚眼の方式はまだ決めていない**——ヘッドレスの静止画で分かったことを書き、決めるのは実機で触ってから（ユーザー）。

- **「画角を広げるだけ」は水平150°では使えない。** 通常の遠近は画面の端ほど引き伸ばすので、正面の机が画面の中央で豆粒になり、端の展示棚だけが巨大になる。上限は 180° 未満（試作では 165° で打ち切り）で、広げるほど悪化する
- **樽型は2方式とも、同じ150°で正面の机を読める大きさに保ったまま、左の作業台から右の展示棚まで入る。** 立体射影と等距離射影は150°ではほとんど見分けがつかない（差が出るのは180°を超えたあたり）
- **`reference/4/2.png`（魚眼の目標）とは、見え方の作りが違う。** あの絵は壁寄りに立った通常の遠近で、中央に固定した立ち位置では同じ絵にならない。**「中央に固定」を守るなら、あの広がりを出す手段は樽型になる**
- **樽型の代償は描画の回数。** 立ち位置から6方向を立方体に描いてから画面に写すので、魚眼の段だけ**1フレームに部屋を6回描く**。ヘッドレス（SwiftShader）では速さを測れないので、実機で確かめる
- **樽型では、マーカーの画面上の位置も同じレンズの式で求める必要がある。** 今の `markerScreen` の射影（通常の遠近）のままでは、カードからマーカーへの点線がずれる
- **ズーム（物へ近づく）は、物ごとの幅から寄る距離を決める。** 最初は一律に「物の1.5m手前」にしたら、幅2.8mの調査ボードが画面からはみ出した。物の幅が水平画角の7割を占める距離（今のサイトの `frameDistance` と同じ考え方）に直すと、ボードもPCのモニター3台も収まった
- **部屋の広さ**: 半径4.5mで、標準（水平73°＝今のサイトの縦45°）で正面の机（幅3m）がちょうど画面に収まる。値は仮で、スライダーで3〜8mを試せる
- **自己紹介の今の見せ方が、部屋では成り立たない。** 今は canvas を透明にして、その**後ろ**にある自己紹介の文字を、3Dが描かれていない画素から見せている（`scene-invariants.md` の「React / R3F の境界」）。**閉じた部屋は壁・床・天井で画面の全画素を覆うので、透明な画素が1つも無い。** 後ろの文字は見えなくなる。樽型が透明を塗りつぶすかという心配（確かめる予定だった3つ目）は、この理由で問題にならなくなった。自己紹介の見せ方は作り直しになる——自己紹介の区画がホログラムなので、ホログラムに文字を流す形が候補

| 標準の水平画角 | **67°** | 今のサイトは縦45°＝16:9で水平73° |
| 魚眼 | **樽型（立体射影）、水平161°** | 「画角を広げるだけ」は採らない |
| ズーム | **物へ近づく**（物の幅が水平画角の7割を占める距離まで、物の正面へ寄る） | 最初「中央のまま画角を狭める」を選び、同じ日に「物へ近づく」へ変更 |
| 明るさ（露出） | 1.75 | 試作の仮の照明に対する値なので、照明を作り直したら意味が変わる。設計の値としては持ち越さない |

- **カメラが中央を離れるのはズームのときだけ。** 標準と魚眼は中央に立ったまま首を振り、ズームで物の正面へ寄って、戻るときに中央へ帰る。今のサイトの「建物へ飛んで寄る→戻る」と同じ形
- **PC のズームで GUI を操作できる大きさになるかは未確認。** 試作は机全体（モニター3台、幅2.1m）が収まる距離に寄るので、中央の画面は画面の3分の1ほど。PC だけ中央の画面に合わせて寄るかは設計で決める
- **魚眼の2方式の違い**（ユーザーに説明した内容）: どちらも「正面からの角度」を「画面の中心からの距離」に置き換えるが、置き換え方が違う。**立体射影**は端に行くほど1°あたりの幅を広げて縦横の比率を保つので、**端の物の形が崩れない代わりに、正面が小さめ・端が大きめ**に写る。**等距離射影**は1°あたりの幅が画面のどこでも同じで、**正面が大きめに写る代わりに、端の物が細く押しつぶされる**。161°の計算値: 正面の大きさは等距離が立体の約1.2倍、画面の左右の端で等距離は横方向が縦方向の約0.70倍（立体は1倍）。210°では差がさらに開く（正面の大きさの比は約1.42倍）。部屋を見渡す用途では端の家具の形が崩れない立体射影が向く、と Claude は勧めた
- **半径を縮めたぶん、物どうしの間隔が詰まった。** 家具の寸法は試作のままなので、3.3m では机の左端（-21°付近）と作業台の右端（341°付近）がほぼ接する。物の角度と寸法は、設計の段階で3.3mに合わせて置き直す

## 試作2: HTML を3Dの中に置く（10/01、ヘッドレスで確認）

PC の画面とホログラムの文字は、どちらも「部屋の中の3Dの物として存在する HTML」（要件）。`sandbox/room-lab.html` に、three.js の `CSS3DRenderer`（CSS の3D変換で、WebGL と同じカメラから見た位置・向きに HTML を貼る）で2つの置き方を足して比べた。R3F では `drei` の `<Html transform>` が同じ仕組みで、2つ目の置き方は `occlude="blending"` にあたる。

| 置き方 | 仕組み | 手前の3Dの物に隠れるか | HTML の後ろに部屋が透けるか |
| --- | --- | --- | --- |
| **手前に重ねる** | HTML の層を canvas の上に置く | **隠れない**（椅子の背もたれの上に画面のタスクバーがはみ出して描かれた） | **透ける** |
| **後ろに置いて穴をあける** | HTML の層を canvas の下に置き、その位置の画素をアルファ0の板で透明に抜く。板は深度を書くので、手前の物は穴の上に描かれる | **隠れる**（背もたれの上端で画面がまっすぐ切れた） | **透けない**（穴の向こうは HTML の層の背景なので、ホログラムが黒い板になった） |

- **結論: PC の画面は「後ろに置いて穴をあける」、ホログラムの文字は「手前に重ねる」。** PC の画面は不透明なので透けなくてよく、手前に椅子やデスクライトが来る。ホログラムは透けないと成り立たず、中央からもズームからも手前に物が来ない（来る配置にしない、が設計の約束になる）
- **クリックは両方の置き方で届いた。** PC に寄っているあいだだけ、canvas の `pointer-events` を外して HTML にクリックとホイールを渡す（ズーム中は見回しが止まっているので取り合わない）。本物のマウスクリックで、アイコン→ウィンドウが開く→×で閉じる、までを確かめた
- **PC に寄るときは、座った目の高さ（1.12m）まで下げる。** 立った高さ（1.55m）のまま寄ると、画面を29°見下ろす形になり、文字が台形に歪んだ。椅子に座る高さに下げると正面から向き合え、本文の22px が読める大きさになった。寄る距離は中央の画面（幅0.62m）が画角の7割を占めるところで、机全体（2.1m）を収めると文字は約6pxになって読めない
- **ホログラムに寄るときは、文字の高さ（1.45m）に目を合わせる**
- **樽型の魚眼の段では HTML を出さない。** CSS の3D変換は通常の遠近しか描けず、樽型に歪んだ部屋と位置が合わない。魚眼の段では画面に貼った絵（テクスチャ）だけを見せる。**開いたウィンドウなど、HTML の今の状態は魚眼の段の絵には映らない**
- **カメラの後ろへ回った HTML は自分で隠す。** CSS の遠近は、カメラの後ろにある板を裏返して巨大に描きうる。前方にあるときだけ出す判定を足した

### 踏んだ罠: 3Dの変換がかかった要素に `overflow: hidden` を付けると、クリックが一切届かない

見た目は正しく描けているのに、画面のどこをクリックしても HTML に届かなかった。原因の切り分け（すべてヘッドレスの `document.elementFromPoint` を格子状に920〜2,880点投げて数えた）:

- 部屋の寸法（m）のまま 0.0005倍で縮める描き方を疑い、HTML 側だけ1m＝1000pxの空間で描き直した → **0点のまま**（この描き直しは、縮尺の極端さを避ける意味で残した）
- 遠近を `transform: perspective()` から `perspective` プロパティへ移す、経路の `pointer-events` を全部 `auto` にする → **0点のまま**
- 遠近を外す → 134点、変換を全部外す → 485点。**遠近がかかったときだけ壊れる**
- 同じ入れ子の最小構成を作って足し引きした: **単純な値で252点 → `overflow: hidden` を足すと0点**。実際の値でも `overflow: hidden` が無ければ1,220点
- **画面（`.desktop`）とウィンドウから `overflow: hidden` を外して解決。** はみ出しを切る必要がある場合は、要素の外側ではなく中身の配置で収める。ウィンドウの本文の `overflow-y: auto`（スクロール）は当たり判定を壊さなかった
- R3F の `drei` の `<Html>` でも同じ仕組みなので、本実装でも同じ縛りがかかるはず（未確認。実装時に同じ方法で数える）

## 設計（10/01 初版）

要件と2つの試作を、本体のコード（Next.js + React Three Fiber）へどう落とすか。今のコードのどこを残し、どこを作り直すかを先に決める。

### 1. カメラ: 「外から回る」を「中央で首を振る」へ

今のカメラは `camera-controls` に「中心を見ながら周りを回る」姿勢（`orbitPose`）を毎フレーム渡している。部屋では次のように置き換える。

| 今 | 部屋 | 扱い |
| --- | --- | --- |
| カメラの位置＝中心から方向 D に半径 r、注視点＝中心 | カメラの位置＝部屋の中央（目の高さ）、注視点＝位置＋方向 D | **方向 D の考え方はそのまま**。向きが「中心を見る」から「中心から見る」へ反転するだけ |
| 巡回の経路 `PLANET_TOUR`（緯度経度の空間で補間した閉曲線、経度の順に巡る） | 首振りの角度そのものを経路上の位置にした水平な輪（`scene/room/tour.ts` の `buildRingTour`）。見上げの角度は停留所の間を閉じたスプラインでつなぐ | **`buildTour()` の再利用は手順1で取りやめた**（下の「手順1の結果」）。外から見た形（`Tour` 型の `direction`/`anchorU`/`nearestU`/`length`）は同じなので、`Scene.tsx` から見た使い方は変わらない |
| 正面のセクション `facingSectionOnPlanet()`（視線に一番近い方向） | 同じ（6か所のうち視線に一番近いもの） | そのまま。ただし6か所目の PC を扱えるように型を広げる（下の 2） |
| ドラッグ・ホイール・2本指・ピンチの入力（`useViewInput`）、ドラッグを離したあとの速度つきの復帰、無操作の自動巡回 | 同じ | そのまま。ドラッグの向きは「世界を掴んで動かす」（試作と同じ。右へドラッグすると視線は左へ） |
| 飛行（`cameraFlight.ts`、自前の時計とイージング、着地での引き継ぎ） | ズーム（物へ近づく）の行き帰りと、視点3段の切り替え | **仕組みは残す。** 補間するものを「位置と注視点」から「首振り・見上げ・前に出る距離・目の高さ・画角」に替える。角度は ±180° をまたいで長い方へ回らないよう `wrapAngle` を通す（今と同じ規則） |

| カメラの「上」を建物ごとに変える（`sectionUp`・`tangentBasis`・`slerpDirection` で補間） | **常に world +Y** | **丸ごと要らなくなる。** 部屋は常に上下が立っている。`scene-invariants.md` の「カメラ — 姿勢と構図」（建物が横倒し・看板が鏡文字になる不具合の項）は、部屋では起きようがない |
| カードを避ける横寄せ（`focalOffsetX`、カメラを横へずらす） | 投影の中心をずらす（`PerspectiveCamera.filmOffset` 相当。樽型の魚眼ではシェーダーの中心をずらす） | 考え方は残す。カメラ自体は中央から動かさない |
| 視点の段（`OrbitZoom` = `"near"` / `"far"`、半径の違い） | `"standard"` / `"fisheye"`（画角と写し方の違い）。ズームは今と同じく「セクションに寄る」 | **型と名前を変える**（カメラを差し替える手順で一緒に）。「orbit」と名の付いた値が回らなくなるので、残すと読み違える |

### 2. 6か所目の PC

PC は巡回に入るが、セクションではない（カードも詳細ページも持たない）。今のコードは「巡回の停留所＝5つの `SectionType`」で組まれているので、**停留所の型を `SectionType` とは別に作る**（例: `Stop = NonNullable<SectionType> | "desk"`）。

- 巡回・正面の判定・マーカーは `Stop` を扱う。カード・詳細ページ・URL の `#products` などは今のまま `SectionType` を扱う
- 正面が PC のときはカードを出さない（要件）。スマホのカードレール（「3枚の窓」）は、正面が PC のあいだ空にする
- PC に寄る操作は、マーカーのタップとズームコントロールの「ズーム」段。寄っているあいだは見回しを止め、canvas のクリックを HTML に渡す（試作2）

### 3. 部屋（今の `PlanetScene` の置き換え）

- **配置は純粋関数に持つ**（新しい `scene/room/`）。部屋の半径・目の高さ・各物の角度と寸法・正面の面までの距離・ズームで寄る距離と目の高さを、three.js を介さないデータとして返し、テストする。試作で踏んだ「正面ではなく背面までの距離で計算していた」を、テストで押さえる
- **描画は R3F のコンポーネント**。形は当面、試作と同じ単純な箱と円柱。作り込みは最後の手順
- 惑星・雑居ビル・プラザと装飾・バス・雲・星（drei の `<Stars>`）は外す。星は丸窓の外の景色に置き換わる

### 4. 魚眼（樽型・立体射影）

- R3F の描画を魚眼の段だけ乗っ取る（`useFrame` に優先度を付けて自分で `gl.render` する）。`CubeCamera` で6方向を描き、全画面の板に立体射影で写す（試作と同じ）
- **マーカーの画面上の位置も立体射影で求める。** 今の `markerScreen`（通常の遠近の射影）に、魚眼の段の射影を足す。純粋関数としてテストする
- 魚眼の段では HTML（PC の画面・ホログラムの文字）を出さない（試作2）

### 5. PC の画面とホログラム（HTML を3Dに置く）

- `drei` の `<Html transform>` を使う。PC の画面は `occlude="blending"`（後ろに置いて穴をあける）、ホログラムの文字は手前に重ねる（試作2）
- **3Dの変換がかかる要素に `overflow: hidden` を付けない**（試作2の罠。付けるとクリックが届かない）。本実装でも同じ方法（`elementFromPoint` を格子状に数える）で確かめる
- **PC の中身と詳細ページは、データと表示の部品を共有する**（「同じ数を2箇所に持たない」）。PC のウィンドウの中に、詳細ページと同じ部品を入れる
- **ホログラムの自己紹介**: 今の「透明な canvas の後ろのクロール」と、その帰り道（スクロールでカメラを引く `aboutReturn`）は外す。文字の流れ方は要件の未決事項

### 6. 照明

- **照明の状態（天井灯・デスクライト・ネオンの色）は AppState に1か所だけ持つ。** 部屋のスイッチと画面のボタンは、どちらもそれを書き換えるだけ。切り替えは頻度が低いので、Context に置いても `<Canvas>` を再調停する代償（`scene-invariants.md` の「React / R3F の境界」）は問題にならない
- 部屋のスイッチは3Dの物なので `pointerClaim` で名乗る（今の太陽と同じ）
- 今の太陽（`Sun.tsx`・`sunLight.ts`）と、太陽の距離から導いた影の範囲は外す

### 7. 自分自身

- 体は視点のカメラの位置に置き、首振りに合わせて向きを変える。**頭は視点のカメラにだけ描かない**（three.js のレイヤー）
- 監視カメラ（右のモニター）は、天井のカメラから部屋を別の描画先に描いてモニターに貼る。**毎フレームではなく間引いて描く**（毎秒10回など。値は実機で決める）
- 映り込みは本物の反射ではなく、薄い絵で済ませる（反射は部屋をもう一度描く代償がある）

### 8. スマホ

- 縦長の画面（390×844 で縦横比0.46）では、水平67°は縦に約110°の画角になる。**スマホ用の画角を別の定数として持つ**（CLAUDE.md の「PC 用の定数をスマホの都合で書き換えない」）。値は、スマホの縦横比で試作を撮って決める
- カードレール・ジェスチャ・`useHandheld` の仕組みはそのまま

## 手順1の結果（10/01）

純粋ロジック3つとテスト33件。画面は変わっていない。テストは574件（+33）、`tsc`・`lint` も通る。

| ファイル | 中身 |
| --- | --- |
| `scene/room/layout.ts` | 部屋の寸法（半径3.3m・目の高さ1.55m・座った目の高さ1.12m・画角）、家具8つの角度と寸法、停留所6つ（`Stop` 型）の注視点、標準の向き（`standardView`）とズームの寄り方（`zoomView`）、正面の停留所（`facingStop`） |

| `scene/camera/fisheye.ts` | 立体射影の写し方と逆写し（`projectStereographic` / `unprojectStereographic`）。魚眼のシェーダーはこの逆写しと同じ式で書く |

### `buildTour()` の再利用は取りやめた

設計では「緯度＝見上げ、経度＝首振り」として今の `buildTour()` を使うつもりだった。書き始めて、**経度が増える向きは、部屋の中から見ると左**だと分かった（`latLonToDirection` は経度0が +Z、経度90が +X。+Z を向いて右手は -X）。そのまま使うと、スクロールで左回りに巡り、ナビの順と逆になる。また `buildTour()` が緯度経度の空間で補間し弧長で測り直しているのは、球面の大円が極側へ膨らむ問題のためで、水平な輪には対応する問題が無い。**首振りの角度そのものを経路上の位置にした**（`u` は一周のうちの割合。弧長ではない）。`length` は一周の 2π にしたので、`Scene.tsx` の `AUTO_ORBIT_SPEED / length` はそのまま「毎秒何ラジアン首を振るか」になる。

### 家具の角度を3.3mに合わせて置き直した

試作の家具の寸法のまま半径3.3mにすると、**机と作業台が1.6°重なり**、扉と作業台の隙間が2.4°しかなかった。机の幅を2.4m→2.2m、通信端末を262°→260°、扉を290°（幅1.1m）→286°（幅1.0m）、作業台を318°（幅1.4m）→316°（幅1.3m）にして、隣り合う家具の間に3°以上の隙間を取った（最小は作業台と机の3.9°）。家具の幅は、中心から見ると**正面の角**のほうが背面の角より広く見えるので、そこで測る。

### 分かったこと: 調査ボードは、部屋の中央からでも画面の7割に収まらない

幅2.9m（ボード2.8m＋枠）を水平67°の画面の7割に収めるには、ボードから約3.1m離れる必要がある。中央からボードまでは約2.9mなので、**中央に立ったままでも約75%を占める。** ズームは中央より後ろへは下がらない作りなので、ボードに寄るときは中央に留まる。部屋の大きさから来る事実で、ボードを狭くするか、ボードだけ画角を広げるかは、見た目を作る段階で判断する。
