# 部屋の中への移行 — 要件と設計

トップページの3Dを「ボクセルの惑星を外から回って見る」から「**ロケットのコロニーの中にある自分の部屋を、内側から見渡す**」へ作り替えるための要件定義と設計。ブランチは `feature/room-world`（2026-10-01 に `main` の `bf2bef8` から切った）。

前回の移行の記録 [planet-migration.md](planet-migration.md) と同じく、要件→設計→各手順の結果の順に書き足していく。完了したら題に「— 完了済み」を付け、現在の構造は `tech.md` と `scene-invariants.md` へ移す。

**経緯**: 世界観は 9/15 に「惑星をやめて衛星（ステーション）へ」と決まり（[devlog 2026-09-15](devlog/202609.md#2026-09-15)）、翌 9/16 未明の会話で「外から見る」から「内側から見渡す」へ、さらに「自分の部屋」へと進んでユーザーが「その方向で行きます」と決めた。**この 9/16 の決定は devlog に書かれないまま**で、10/01 に会話ログから見つけ直した（[devlog 2026-10-01](devlog/202610.md#2026-10-01)）。`sandbox/station-draft*.html` は外から見る案の頃の試作で、この移行の設計の根拠には使わない。

### 間取り（10/01 のたたき台に対するユーザーの回答）

真上から見た図。サイトを開いて最初に正面に来るのが PC で、スクロールで右へ首を振る。

```
                 [ 机：デスクトップPC ＋ ホログラムのデバイス ]
                   PC（正面・ホーム）   ホログラム（自己紹介）
   通信端末・扉                                   展示棚
   （連絡先）                                     （制作実績）

                           ● 立ち位置

   調査ボード                                     技術書の本棚
   （経歴・活動）                                 （スキル）
                  丸窓 ＋ その下にハンモック
```

- **並び（ユーザー承認）**: PC → ホログラム（自己紹介）→ 展示棚（制作実績）→ 本棚（スキル）→ 調査ボード（経歴・活動）→ 通信端末（連絡先）→ PC。**PCの右隣から、今のヘッダーのナビと同じ順**なので、ナビで飛んでも部屋の中の位置関係と矛盾しない
- **扉と丸窓を置く**（ユーザー）。扉は通信端末の脇（連絡先＝外とつながる場所）。丸窓はコロニーの縦穴を覗く窓（9/16 の案）
- **ハンモックを置く**（ユーザー）。セクションではない、生活の物。巡回の途中で何も起きない区間になるが、「自分の部屋」らしさを出す
- 調査ボードは横に長いので、ほかの物より広い角度を取る
- **扉から机までの区間に、作業台（3Dプリンタ）を置く**（ユーザー）。`reference/4/1.png` で何も無かった区間を埋める。展示棚に並ぶ物を「ここで作っている」という物語にもなる
- **丸窓とハンモックは、本棚と調査ボードの間（PC の真後ろ）。** 丸窓の下にハンモックを吊るし、寝転んで窓の外を眺める場所にする。セクションではない区間を1か所にまとめる（Claude 案。この配置で生成した `reference/4/1.png` をユーザーが「いい感じ」と評価）

### 決まっていないこと


- **PCのGUIの作り方。** 3Dオブジェクトとして存在させる方法は2つある:
  - **HTML を3D空間に置く**（`drei` の `<Html transform>`。CSS の3D変換で、モニターの面に HTML の要素を貼る）。見た目は部屋の中の物のまま、文字は本物の HTML なので検索・スクリーンリーダー・文字の選択が効く。**こちらを第一候補にする**
  - **画面をテクスチャに描く**（canvas に描いた絵をモニターの面に貼る）。3Dとしては素直だが、中身が絵になるので検索にも読まれない。AdSense で「有用性の低いコンテンツ」と判定された経緯（2026-09-19）があり、読める中身を絵に置き換える方向には動かせないので採らない
  - HTML を3Dに置く方式で確かめること: **手前の3Dの物に隠れるか**（DOM は canvas の外にあるので、そのままでは3Dの物の手前に出る。`drei` の `occlude` で足りるか）、**透明な canvas の3層構成**（`scene-invariants.md` の「React / R3F の境界」）との重なり順、PCの画面の中の操作とカメラのドラッグの取り合い（`pointerClaim` と同じ問題）
- **PCの中身と詳細ページ（シート）の関係。** 5区画を押したときは今の詳細ページが開く想定なので、同じ情報がシートとPCの2か所に出る。**データと部品は1つにして両方から使う**（「同じ数を2箇所に持たない」）。ノートのように別のページへ移るものを、PCの中でどう扱うかも決める
- **PCが正面のあいだ、カードの場所が空くこと。** PC はカードを出さないので、PC では画面左のカード（スマホでは下のカードレール）が消える。スマホのレールは「3枚の窓」として組んであり（`scene-invariants.md` の「スマホ」節）、6か所中1か所だけ窓が空になる扱いを決める
- **展示棚の品をボクセルにするか。**
- **左のモニターに流す動画と、右の監視カメラの映像の中身。** 右は部屋の主が映る映像なので、実写の動画・写真か、絵にするかを決める（本人の姿をサイトに出すことになる）。どちらも素材が要るので、`public/` に置くファイルの大きさ（配信サイズ）も一緒に決める
- **樽型の魚眼が実機で重くないか。** 方式は決まった（立体射影・161°）が、魚眼の段は1フレームに部屋を6回描く。スマホも含めて実機で確かめる
- **ホログラムの文字の流し方。** 今のクロール（`reference/2/image9.jpg` に合わせた奥へ流れる列、自動再生、読み終えたらホームへ戻る）をどこまで引き継ぐか。今の自己紹介はシートを持たない唯一のセクションで、「読み終えること」が帰り道になっている（`tech.md` の「自己紹介の帰り道は『読み終えること』」）
- **照明の細部。** ネオンの色の組み合わせをいくつ用意するか（今はシアンと琥珀）、部屋のスイッチをどこに付けるか、画面のボタンをどこに置くか。**照明の状態は1か所に持ち、部屋のスイッチと画面のボタンはどちらもそれを書き換えるだけにする**（「同じ数を2箇所に持たない」）。部屋のスイッチは3Dの物なので、空タップの停止と混ざらないよう `pointerClaim` で名乗る（今の太陽と同じ）
- **参考写真。** CLAUDE.md の「値は参考写真・実測から導く」に従うには、部屋の構図の参考が要る。`reference/3`（旧 `reference/now`）の12枚は外観・街路・通路が中心で、個人の部屋の写真は無い。10/01 に生成画像2枚を `reference/4` に置いた（下の「参考画像」）。構図・雰囲気の参考にはなるが、生成画像なので寸法を導く根拠にできるかは、使う場面ごとに判断する

### 魚眼の2案

| | 画角を広げるだけ | 魚眼レンズ風の歪み |
| --- | --- | --- |
| 見え方 | 視野角を広げる（今の `CAMERA_FOV` は 45°）。画面の端の物ほど引き伸ばされる | 中央が膨らみ、端が丸く曲がる。広く写しても端が引き伸ばされない |
| 実装 | カメラの値1つ。軽い | 画面全体を描き直す処理（ポストプロセス）が要る |
| 既存の仕組みとの関係 | マーカーの画面上の位置・大きさの計算（`markerScreen`・`pixelsPerWorldUnit`）はそのまま成り立つ | **画面上の位置がレンズの式でずれるので、カードからマーカーへの点線の射影も同じ式で曲げる必要がある。** また、自己紹介の文字より3Dを手前に出す仕組みは canvas の透明に依存していて、ポストプロセスがアルファを塗りつぶすと壊れる（ネオンのブルームと同じリスク） |

## 試作 `sandbox/room-lab.html` の結果（10/01、ヘッドレスで確認）

円形の部屋（半径4.5m、壁の高さ3.4m、目の高さ1.6m）に要件の物を仮の形で置き、中央から見回す試作。**魚眼の方式はまだ決めていない**——ヘッドレスの静止画で分かったことを書き、決めるのは実機で触ってから（ユーザー）。

- **「画角を広げるだけ」は水平150°では使えない。** 通常の遠近は画面の端ほど引き伸ばすので、正面の机が画面の中央で豆粒になり、端の展示棚だけが巨大になる。上限は 180° 未満（試作では 165° で打ち切り）で、広げるほど悪化する
- **樽型は2方式とも、同じ150°で正面の机を読める大きさに保ったまま、左の作業台から右の展示棚まで入る。** 立体射影と等距離射影は150°ではほとんど見分けがつかない（差が出るのは180°を超えたあたり）
- **`reference/4/2.png`（魚眼の目標）とは、見え方の作りが違う。** あの絵は壁寄りに立った通常の遠近で、中央に固定した立ち位置では同じ絵にならない。**「中央に固定」を守るなら、あの広がりを出す手段は樽型になる**
- **樽型の代償は描画の回数。** 立ち位置から6方向を立方体に描いてから画面に写すので、魚眼の段だけ**1フレームに部屋を6回描く**。ヘッドレス（SwiftShader）では速さを測れないので、実機で確かめる
- **樽型では、マーカーの画面上の位置も同じレンズの式で求める必要がある。** 今の `markerScreen` の射影（通常の遠近）のままでは、カードからマーカーへの点線がずれる
- **ズーム（物へ近づく）は、物ごとの幅から寄る距離を決める。** 最初は一律に「物の1.5m手前」にしたら、幅2.8mの調査ボードが画面からはみ出した。物の幅が水平画角の7割を占める距離（今のサイトの `frameDistance` と同じ考え方）に直すと、ボードもPCのモニター3台も収まった
- **部屋の広さ**: 半径4.5mで、標準（水平73°＝今のサイトの縦45°）で正面の机（幅3m）がちょうど画面に収まる。値は仮で、スライダーで3〜8mを試せる
- **自己紹介の今の見せ方が、部屋では成り立たない。** 今は canvas を透明にして、その**後ろ**にある自己紹介の文字を、3Dが描かれていない画素から見せている（`scene-invariants.md` の「React / R3F の境界」）。**閉じた部屋は壁・床・天井で画面の全画素を覆うので、透明な画素が1つも無い。** 後ろの文字は見えなくなる。樽型が透明を塗りつぶすかという心配（確かめる予定だった3つ目）は、この理由で問題にならなくなった。自己紹介の見せ方は作り直しになる——自己紹介の区画がホログラムなので、ホログラムに文字を流す形が候補

### ユーザーが試作で選んだ値（10/01）

| 項目 | 値 | 補足 |
| --- | --- | --- |
| 部屋の半径 | **3.3m** | 試作の初期値 4.5m から縮めた |
| 目の高さ | **1.55m** | |
| 標準の水平画角 | **67°** | 今のサイトは縦45°＝16:9で水平73° |
| 魚眼 | **樽型（立体射影）、水平161°** | 「画角を広げるだけ」は採らない |
| ズーム | **物へ近づく**（物の幅が水平画角の7割を占める距離まで、物の正面へ寄る） | 最初「中央のまま画角を狭める」を選び、同じ日に「物へ近づく」へ変更 |
| 明るさ（露出） | 1.75 | 試作の仮の照明に対する値なので、照明を作り直したら意味が変わる。設計の値としては持ち越さない |

- **カメラが中央を離れるのはズームのときだけ。** 標準と魚眼は中央に立ったまま首を振り、ズームで物の正面へ寄って、戻るときに中央へ帰る。今のサイトの「建物へ飛んで寄る→戻る」と同じ形
- **PC のズームで GUI を操作できる大きさになるかは未確認。** 試作は机全体（モニター3台、幅2.1m）が収まる距離に寄るので、中央の画面は画面の3分の1ほど。PC だけ中央の画面に合わせて寄るかは設計で決める
- **魚眼の2方式の違い**（ユーザーに説明した内容）: どちらも「正面からの角度」を「画面の中心からの距離」に置き換えるが、置き換え方が違う。**立体射影**は端に行くほど1°あたりの幅を広げて縦横の比率を保つので、**端の物の形が崩れない代わりに、正面が小さめ・端が大きめ**に写る。**等距離射影**は1°あたりの幅が画面のどこでも同じで、**正面が大きめに写る代わりに、端の物が細く押しつぶされる**。161°の計算値: 正面の大きさは等距離が立体の約1.2倍、画面の左右の端で等距離は横方向が縦方向の約0.70倍（立体は1倍）。210°では差がさらに開く（正面の大きさの比は約1.42倍）。部屋を見渡す用途では端の家具の形が崩れない立体射影が向く、と Claude は勧めた
- **半径を縮めたぶん、物どうしの間隔が詰まった。** 家具の寸法は試作のままなので、3.3m では机の左端（-21°付近）と作業台の右端（341°付近）がほぼ接する。物の角度と寸法は、設計の段階で3.3mに合わせて置き直す

## 設計の見通し（要件が固まってから確定する）

要件の段階で分かっている、今の仕組みとの関係だけを書く。

- **「方向」で考える部分は残せる見込み。** 今のカメラは「中心から見た方向」でセクションを扱っている（正面のセクションは視線の方向に最も近いもの＝`facingSectionOnPlanet()`、ツアーは方向の閉曲線）。中央に固定して見回すなら、**「中心から外を見る方向」として同じ考え方が使える**——惑星では中心を見る向き、部屋では中心から見る向き、と向きが反転するだけ
- **自由回転の「回る」は「首を振る」になる。** `orbitPose`（中心を見ながら周りを回る）は「中心に立って外を向く」姿勢に置き換わる。ドラッグ・ホイール・スクロールでツアーを進める入力の流れ、ドラッグ後の復帰、飛行の仕組み（`cameraFlight.ts`）は、姿勢の組み方だけ差し替えて引き継げる見込み
- **ズームコントロールの3段とピンチはそのまま対応する**: 俯瞰→魚眼、標準→標準、正面の建物→ズーム
- **消えるもの**: 惑星の土台・雑居ビル・プラザと装飾・バス・雲、`scene-invariants.md` の「球面という前提」の大半（地形、法線に立つ建物）、惑星の半径 16.8 から導いた定数一式（`NEAR_ORBIT_RADIUS`・`NEAR_VERTICAL_SHARE`・スマホの高度・影の範囲・太陽の窓）
- **決めていない大物**: About のクロール（今は惑星が文字の手前に来る構図）、スマホの構図（今は「惑星の縁が画面の3分の1」という規則）
