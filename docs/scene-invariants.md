# 3Dシーンの不変条件

**トップページは、ロケットのコロニーの中にある円い部屋。カメラは部屋の中央に立って首を振り、区画を選ぶとその物の前へ寄る。**

このファイルは「壊しやすい箇所と、なぜそれが壊れるのか」の台帳。**3Dに触れる変更の前に読む**（[AGENTS.md](../AGENTS.md) の「作業前に読むもの」参照）。アーキテクチャの全体像は [tech.md](tech.md)、部屋への移行の経緯と各手順の実測は [room-migration.md](room-migration.md) にある。

各項目には**実測値と、一度試して捨てた案**を残してある。同じ案が再提案されるのを防ぐのが目的なので、書き換えるときも数字と却下理由は落とさないこと。惑星の頃の項目（球面、建物ごとのカメラの「上」、太陽、クロールなど）は [planet-archive.md](planet-archive.md) に本文のまま移した。

## 部屋とカメラ

- **カメラの「上」は常に world +Y。** 部屋は横倒しにならない。惑星の頃の「建物ごとに `camera.up` を変える」仕組み（看板が鏡文字になる不具合への対処）は、部屋では起きようがないので外した
- **姿勢は `RoomPose`（床の上の場所・首振り・見上げ・前に出る距離・目の高さ・画角・レンズ・2つのずらし）で持ち、カメラから読み戻さない。** 位置と向きは `placeCamera` が毎フレーム直接書く。`camera-controls` は外した（回るための道具で、中央で首を振るだけなら不要）
- **配置は `scene/room/layout.ts` の純粋関数が正。** 家具の角度と寸法、停留所の注視点、ズームの寄り方、モニター・キーボード・椅子の位置。描画（`RoomScene`）も HTML の板（`room/screens.ts`）も、ここの数から位置を取る。**家具は「正面＝ローカル +Z＝中心向き」で置く**——試作で、ズームの立ち位置を正面ではなく背面からの距離で計算する取り違えを踏んだ（`dist + d/2` と書いて奥行きぶん寄りすぎた）。テストで押さえてある
- **家具どうしの隙間は、一周の継ぎ目をまたいで符号付きで測る。** `% 360` で丸めると、机と作業台の1.6°の重なりが「358.4°の隙間」として通った（手順1）
- **カメラの毎フレームの処理（`CameraController` の `useFrame`）は優先度 -1。** R3F の `useFrame` は同じ優先度なら登録順に走り、部屋（マーカーを含む）が先にマウントされているので、優先度0のままだと**マーカーが前のフレームのカメラで射影し、点線の先が1フレーム遅れる**（手順3で見つけた。手順2で `camera-controls` を外したときに入っていた）。負の優先度は描画を乗っ取らない
- **ズームの段は `ViewZoom`（`standard` / `fisheye`）で、ズーム（寄る）は `activeSection`（`Focus`）。** 寄るのは区画5つと PC。PC に寄っているあいだを別のフラグで持たない（区画と PC に同時に寄っている状態が作れてしまう）
- **調査ボード（幅2.9m）は中央からでも画面の約75%を占める。** 7割に収めるには約3.1m離れる必要があるが、中央からボードまで約2.9m。ズームは中央より後ろへ下がらない作りなので、ボードでは中央に留まる
- **座る位置は端末によらず固定**（デスクトップの画角で「中央の画面が7割」になる距離、画面から約0.86m）。スマホの狭い画角で計算し直すと、椅子より後ろに座らされる。**椅子は座った目から置く**（背もたれは目の15cm後ろ）。手で置いていた頃、背もたれが座った目の13cm前に立ち、スマホで画面の下半分を塞いだ（手順4）
- **中央から PC の画面の下端への視線は、椅子の位置で床から1.13mを通る（2026-10-02 の人物の寸法で1.14m：目が1.49m に下がり、椅子の背は座った目の30cm 後ろへ下がった）。背もたれ（0.98m）はそれより低く保つ。** 試作の1.19mでは、ホームの画面の真ん中を黒い板が塞いだ（手順2）。テストあり
- **座ったときは、画面の上端と手の中間を見る**（`seatedPitch`）。画面の中心を見ると、キーボードの上の手は 16:9 の画面の下端より約4°下で見えなかった
- **下を向くほど目が前へ出る（`headLean`、最大7cm）。ただし15°より深く下を向いたときから。** 目を体の真上に固定したままだと、真下を向いても胸の上の面しか見えなかった。12cmにすると足が目より後ろに回って画面の外へ出た。15°より浅い角度で出すと、区画の正面の見方（どれも±10°以内）が数cmずれる
- **見上げ・見下ろしの上限は70°。** 55°では 16:9 の画面の下端が75°までしか届かず、自分の脚が見えなかった

## レンズ（標準⇄魚眼）

- **レンズは1本の式 `r = tan(θ/k)/tan(H/k)`（`camera/fisheye.ts`）。k=1 が通常の遠近、k=2 が立体射影。** どの k でも画面の左右の端は水平画角 H の位置に来るので、標準（k=1・見回すとき90°）から魚眼（k=2・161°）への飛行で k と画角を一緒に補間すれば、部屋が飛行のあいだに曲がっていく。**画角を広げるだけの魚眼は却下済み**（試作: 水平150°で正面の机が豆粒になり、端の展示棚だけが巨大になった）
- **魚眼の描画、マーカーの位置と大きさ、クリックの当たり判定は、すべて同じ式で求める。** シェーダー（`LENS_FRAGMENT_SHADER`）は `unprojectLens` を画素ごとに、マーカーは `projectToScreen` と `lensPixelsPerRadian`、クリックは R3F の `events` の `compute` を差し替えた `screenRay`。**差し替えを外すと、魚眼の段でマーカーに一度も当たらなかった**（点線の終端から40pxの範囲でホバー0回）
- **k=1 のまま立方体を経由して描くと、直接の描画と一致する**（色は7点で±1以内、ずれ0px、全体の平均の差は輝度2.3＝アンチエイリアスとミップマップのぼけ方の違い。手順3では6点で完全一致）。シェーダーの式・ずらし・トーンマッピングと色空間の扱いを変えたら、同じ方法で確かめる。**点だけでなく差分の画像も見る**——床の不具合は、確かめた点が画面の下端に無かったので見逃していた
- **魚眼の段は1フレームに部屋を6回描く**。実機の速さは未計測
- **立方体の面は、アンチエイリアスをかけて、画面に必要な細かさで描く**（`LensRenderer` の `drawCube`）。面ごとに MSAA 4倍・半精度の作業用の描画先へ描き、トーンマッピングしながら 8bit sRGB の立方体へ写し、ミップマップを作る。面の大きさは `cubeFaceSize`（面の中心の px/rad が、魚眼の画面の中心の px/rad 以上。上限はデスクトップ1536px・スマホ1024px）。**`CubeCamera.update` で面へ直接描く形に戻さない**——アンチエイリアスが無く、面が1024px 固定で Retina では中心で約1.85倍に引き伸ばされ、輪郭が階段状に拡大された（2026-10-01 ユーザー「魚眼時にオブジェクトがガビガビ」）
- **トーンマッピングは立方体へ写すときに済ませ、魚眼のシェーダーでは画面向けの符号化だけをする。** three.js は画面に描くときしかトーンマッピングしないので、写すシェーダーに three.js の `ACESFilmicToneMapping` を一字一句写してある。8bit の立方体にトーンマッピング前の値を入れると、ネオンなど1を超える明るさが切れる
- **床と天井は円ではなく、奇数に分割した正方形の板**（`FLOOR_SEGMENTS` = 9、外へはみ出す分は壁の裏で見えない）。**カメラの真下・真上に頂点を置かない。** 立方体の面のカメラは部屋の軸にそろっているので、円の中心の頂点がその4つのカメラの平面上（w=0）に乗り、魚眼で床の三角形が机の手前に描かれた（下の帯の明るさが直接の描画24に対し10.7。床を隠すと21に戻り、板にして25.6）。手順3のときから起きていたが、確かめた6点が画面の下の端に無かったので気づかなかった
- **魚眼の絵は不透明に描く**（アルファ1）。立方体に PC の画面の穴（アルファ0）が写ると、そこが黒く抜ける。穴は `SCREEN_HOLE_LAYER` に置き、立方体のカメラには描かせない
- **ズームは常に通常の遠近（k=1）。** HTML を3Dに置いた板は通常の遠近でしか描けない
- **カードを避ける横寄せと、スマホの縦のずらしは、投影の中心をずらす**（`setViewOffset`、魚眼ではシェーダーの `uShift`）。カメラ自体は中央から動かさない。ずらしは画面の幅・高さに対する割合なので、ウィンドウの大きさが変わっても組み直しが要らない

## HTML を3Dに置く層（PC の画面・ホログラム）

- **drei の `<Html transform>` は使わず、自前の CSS3D の層にした**（`camera/cssView.ts`＋`hub/room/RoomHtml.tsx`）。drei は遠近の中心を画面の中央に固定し、投影の縦の倍率しか読まないので、**投影をずらしている部屋のカメラでは HTML が WebGL の画面からずれる**。自前の層では、ずらしを `perspective-origin` とカメラの変換の両方に入れて「出来上がった絵ごと平行移動」にした。もう1つ、drei の `occlude="blending"` は canvas 要素の z-index・position・pointer-events を書き換える
- **CSS の合成が WebGL の射影と一致することをテストで押さえてある**（`cssView.test.ts`）。テストの側で CSS の規則（transform-origin・perspective-origin・遠近の割り算）を独立に書き、PC の画面の四隅が4つの構図で一致すること。**CSS の射影とレンズの射影は同じカメラの基底（`cameraBasis`）を使うので、基底の符号を揃って間違えても一致してしまう。** 「注視点の上はカメラ空間で上、右は右」を別に確かめている
- **3Dの変換がかかった箱に `overflow: hidden` を付けない。** Chrome はその中の当たり判定を一切返さなくなる（見た目は正しい）。試作2で、最小構成で252点→0点。層・カメラ・板・PC の GUI の外枠には付けていない。中身の部品（制作実績のカードなど）に付いている分は当たり判定を壊さなかった（3枚とも中心に当たった）。**足したら `document.elementFromPoint` を格子状に投げて数える**（座った状態の PC の画面で897点中897点）
- **HTML の世界は1m＝1000px**（`CSS_UNITS`）。極端に小さな倍率は最初から避けた
- **PC の画面は canvas の後ろに置き、canvas に穴（深度を書き、色とアルファ0の板）を開ける。** 手前の椅子やランプが画面を隠せる。**ホログラムは canvas の手前に重ねる**（透けないと成り立たない）。**ホログラムの手前に物を置かない**（手前に来た物も文字の下に描かれる）
- **穴と HTML は同じ条件（`panelShown`）で出し入れする。** 通常の遠近のときだけ、カメラの前方にあり、表から見ているときだけ。穴だけ残ると、後ろに何も無い黒い穴になる
- **板の CSS の変換は描画後に ref から書く。** 行列は配置の三角関数から作る数で、サーバー（Node）とブラウザで最後の桁が一致する保証が無い。レンダーで書いたら、ハイドレーションで属性の食い違いの警告が出た（手順5）
- **座っているあいだだけ、canvas はポインタを通す**（`Scene` の `interactive` と、包む div の `pointer-events-none`）。見回しはズーム中は止まっているので取り合わない。PC の GUI の根に `data-ui` を付け、スマホの空タップの一時停止と混ざらないようにしてある

## カメラ — 自由視点の首振り

- **部屋は勝手に回らない**（2026-10-01 ユーザー）。代わりに、ゲームの一人称視点のような軽い揺れ（`idleSway`、首振り±0.45°・見上げ±0.3°・目の高さ±6mm、仮）を描く姿勢に足す。**揺れは `poseRef` に入れない**——飛行は `poseRef` から始まるので、入れると揺れの途中の値から飛び立つ。描いて配る姿勢（`publishView`）には入れるので、マーカー・点線・部屋の中の HTML は絵と一緒に揺れる
- **揺れは部屋の時計（`sceneClock`）で動く**。一時停止で止まる（ヘッドレスで、停止中の2枚の差が0.0）。**PC と自己紹介に寄っているあいだは揺れを0へ減衰させる**（読んでいる文字が揺れると読みにくい）。OS の「視差効果を減らす」（`prefers-reduced-motion`）でも0
- **巡回に沿うのは、ホイール・2本指・カードの送り・区画からの帰り・リセットのあとだけ**（`followTourRef`）。**マウスの照準と指のドラッグはそれを外し、向けた向きのまま留まる。** 惑星の頃は、アイドルで進み続ける巡回へ「速度で戻す」仕組み（`ORBIT_RETURN_SPEED`）があった。目標が逃げ続けるから要った仕組みで、アイドルの回転を外したので一緒に外した。経緯と実測は [planet-archive.md](planet-archive.md) の「カメラ — 自由回転の高度と復帰」
- **首振りの減衰は実時間で回す**（`dampFraction`、λ=5）。一時停止しても読み手のホイールやカードの送りは届く。惑星の頃は一時停止の時計で減衰していたので、停止中はホイールで向きが変わらなかった
- **首振りの向きの真実は `yawRef`/`pitchRef`（と目標）、巡回の位置の真実は `tourURef`。** カメラから読み戻さない。ドラッグ中も `tourURef` を一番近い位置へ追従させるので、ドラッグのあとのホイールは近くから続く
- **マウスはゲームの一人称のように照準を向ける**（2026-10-02 ユーザー。マウスのドラッグから置き換えた）。部屋を1回クリックするとマウスをつかみ（Pointer Lock API、対象は canvas）、カーソルが消えて照準（画面の中央の◯、ユーザーの指定）が出る。マウスを右へ動かすと右を、上へ動かすと上を向く（`mouseLook`、0.002 rad/px、仮）。**向きは減衰させずにその場で変える**——ホイールの λ=5 の追いかけ（約0.2秒）を通すと、照準が手から遅れる。保っている角度と目標の両方に同じ量を足すので、ホイールの滑りの途中でも続きは残る。マウスはもうドラッグしない
- **つかんでいるあいだのクリックは照準＝画面の中央を撃つ**（`roomEvents` の `compute`）。ロック中のブラウザはイベントの座標をロックした瞬間の位置に止めるので、座標のまま光線を出すと、照準と関係ない場所に当たる
- **照準は視線の軸の上にない。** デスクトップの自由視点はカードを避けて投影を右へずらしている（`ORBIT_CARD_SHARE` 0.22）ので、軸は幅の61%にあり、画面の中央はその約12°左を見ている。最初は照準を軸（`projectToScreen([0,0,-1])`）に置いたが、ユーザーが中央を選んだ。**そのため、つかんでいるあいだはカードの「正面」（`facingStop`）も中央の向き（`frameCentreDirection`）で決める。** 軸のままだと、照準を机のマーカーに合わせているのにカードは「自己紹介」を出していた（ヘッドレスで撮って見つけた）
- **マウスを返すのは Esc（ブラウザの決まり）と、区画に寄ったとき**（`lockedRef` が立ったら `exitPointerLock`）。寄った先のカード・PC の画面・詳細ページはカーソルで読むため。マーカーとスイッチのクリックは、つかむ前でもそれらのもの（`pointerClaim`）で、つかまない。Esc の直後の再ロックはブラウザが少しのあいだ断るので、失敗は黙って捨てる（もう一度クリックすれば取れる）
- **指のドラッグ（スマホ）は「世界を掴む」**（右へドラッグすると視線は左へ。2026-10-01 ユーザーの決定。マウスとは逆向き）。**ホイールを下へ回すと右を向く**（＝ナビの順に進む）
- **巡回の経路は首振りの角度そのもの**（`room/tour.ts`）。惑星の `buildTour()` は経度が増える向きが部屋の中から見ると左で、そのままだとナビの順と逆に巡るので使わなかった

## カメラ — キーで歩く・跳ぶ

- **床の上の場所は `RoomPose` の `x`/`z`、区画への一歩は `forward`**（2026-10-02）。前は「中央から見ている向きへ何m 出たか」の1つの値しか持てず、キーで自由に歩けなかった。体・座る度合い・歩数・椅子は、どれも `floorSpot`（場所＋一歩、`headLean` は含めない）から読む
- **歩くのは自由視点だけ。** 区画に寄っている・詳細ページが開いている・飛行中は、キーは何もしない（跳んでいれば着地させる）。区画への構図は中央から組んであるので、寄るときはいまの場所から歩いて行き、離れるとその場所へ歩いて戻る。ロゴ／HOME は中央へ戻す
- **キーは打つ場所で拾わない**: 入力欄（`input`/`textarea`/`select`・contenteditable）に打っている文字、Ctrl/⌘/Alt 付きのショートカット。キーは配列に依らない位置（`e.code` の `KeyW` など）で読む。ウィンドウを離れたら全部離したことにする（タブを切り替えて戻ったら歩き続けていた、を防ぐ）。Space は押すたびに1回だけ跳ぶ（押しっぱなしで着地のたびに跳ばない）。**ボタンやリンクにフォーカスがあるときの Space はそちらのもの**（キーボードで操作する人がボタンを押すキー）。跳ぶときは `preventDefault` でページを送らない
- **壁と家具は押し戻しで止める**（`room/floor.ts`）。家具の床の形を体の半径（22cm、仮）だけ広げ、中に入った場所を前か横の近いほうへ押し出す。斜めにぶつかると前面に沿って滑る。押し戻した分は速さからも消す（壁に向かって押し続けない、テストあり）。椅子は転がるので含めない
- **跳ぶ高さは描く姿勢にだけ足す**（揺れ・歩きの上下と同じ。`poseRef` には入れない）。体は一緒に上がり、足は床を離れる（脚の骨は伸びない）。空中では歩きの上下は0。跳ぶ計算は等加速度の式そのまま（速さを先に進めてから高さを進める形では、60fps で45cm に2.5cm 届かなかった）
- **歩いて机の前を通っても椅子は動かない。** 椅子が背後へ回り込むのは、机の正面を向いて座る場所へ近づくときだけ（向きが座る向きから約40°以内）。この条件が無いと、キーで机の前を横切るだけで椅子が追ってきた
- **向きを変えながら歩く飛行は、道のりの長さに沿って進める**（`walkPath`）。姿勢を均等に混ぜると、外へ出るほど向きの変化で横へ振られて床の上の速さが偏り、PC の向きから展示棚へ寄ると歩く速さを2.1%超えた

## カメラ — 行き先と飛行

- **カメラの行き先を決める effect は `scene/Scene.tsx` に1つだけ。** 経路は5つ（区画か PC に寄る／リセットで巡回の先頭＝PC へ／区画を離れて巡回を再開／自由視点の段が変わった／初回）
- **自由視点へ降りる飛行は、着地で首振りと見上げの値（と目標）を揃える**（`RoomFlight.land`）。カメラと向きの値は別々の真実で、揃えないと次のアイドルフレームが飛行前の角度から damp を再開する（惑星で実測: セクション→ホーム最大36°、ロゴ→ホーム最大180°の巻き戻り）
- **飛行は自前の時計とイージングで回す。** 角度は `wrapAngle` で短い方へ回す
- **区画へ寄る飛行は「歩く」**（`camera/walkFlight.ts` の `planRoomMove`）。加速0.35秒・巡航1.5m/s・減速0.35秒（仮）で、全体を1本のイージングで滑らせない（最高速が平均の1.875倍になり、1.9m を1.1秒で瞬間に約3.2m/s だった）。PC は「歩く → 引いた椅子に座る → 椅子ごと寄る」、離れるときはその逆。**座ってから寄るので、歩いているあいだ目の高さは立った高さのまま**（テストあり）。歩かない飛行（その場で回る・レンズの段の切り替え）は今までどおりの滑らかさ。`FLIGHT_SECONDS`／`RETURN_SECONDS` は**最短の長さ**になり、短い歩きはそれに合わせて遅く歩く（詳細ページの裏で始まる帰り道を、ページが退いたあとまで残すため）
- **戻るときは後ろ歩き**（カメラは区画を向いたまま）。振り向いて歩き、また振り向く形は、カメラが一周近く回るので採らなかった
- **飛行の初回フレームには `delta` を加算しない**（`primed`）。`frameloop="demand"` の裏では毎秒1フレームなので、加算すると1フレームで飛行が終わる。1フレームの上限は `MAX_FLIGHT_STEP`（0.1秒）

## スマホ（`lg` 未満のタッチ画面）

- **「スマホか」を判定するのは `state/useHandheld.ts` ただ1つ。** 述語は `(pointer: coarse) and (max-width: 1023px)` で、両方が要る。`Hub` と `Scene` がそれぞれ自分で呼ぶ
- **スマホの画角は別の定数**（`HANDHELD_STANDARD_VFOV` 縦78°、`HANDHELD_FISHEYE_HFOV` 横90°。どちらも仮）。デスクトップの横67°をスマホで使うと縦約110°で天井が3分の1を占め、161°の魚眼は縦約245°になって真上と真下を越えて折り返す。**デスクトップの定数をスマホの都合で書き換えない**
- **スマホでは被写体を上へずらす**（`cardLift`、`1 − 664/844 = 0.21`）。カードレールの上端の実測（664px、真ん中のカードの上辺で測る。両隣や HOME で測って2回間違えた）から、レールの上の帯の真ん中へ。惑星では逆に下げていた（水平線を入れるため）
- **カードレールは3枚の「窓」で、両隣は部屋の順**（`adjacentSection`、PC を飛ばす）。手順9まで、レールの両隣だけが惑星の巡回の順のままで、スワイプで実際に向かう区画と食い違っていた。テストの側も惑星の関数と比べていたので緑だった。今は「自己紹介の両隣はお問い合わせと制作実績」を書き下したテストがある
- **3Dに置いた HTML は、スマホでは小さすぎて読めない。** 画面の幅いっぱいでも PC の画面（1400px）は約375pxに縮む。ホログラムの文字はスマホでは平らな層で出している（仮）。PC の扱いは未決
- 以下は惑星の頃から変わらない: 2本指は「間隔が変わる＝ズーム」と「一緒に動く＝巡回」のどちらかにラッチし、先着順で決めない（`twoFingerGesture`）／2本指スクロールの率は `DRAG_SENSITIVITY`／トラックパッドのピンチは `ctrlKey` 付きの `wheel` で来るので、2本指の機能は両方の経路に足す／タップの判定は `useTapGesture` として別に持つ／シーンの中の物（マーカー・照明のスイッチ）は `pointerClaim` で名乗る／レールのジェスチャはボタンの上のプレスを無視する／レールの追従は見た目だけで、位置を状態にしない。数字と経緯は [planet-archive.md](planet-archive.md) の「スマホ」

## 照明

- **照明の状態（天井灯・デスクライト・ネオンの色）は AppState に1か所。** 部屋のスイッチ板とヘッダーのメニューは `flipLight` を呼ぶだけ
- **環境光の底は試作の2倍（半球光1.2・環境光0.5）。下げない。** 規則は「天井灯とデスクライトを消しても、どの区画の被写体も、全部点けたときの一番暗い被写体（本棚、輝度43）より暗くならない」。×1.5では本棚が38で下回った。表は `lighting.ts` と room-migration.md の「手順6の結果」
- **明るさを画面全体の暗い画素の割合で測らない。** 全部点けても本棚の正面の80.5%が輝度40未満（本の色）。被写体の位置の箱で測る（惑星の「1つの素材の領域で測る」と同じ）
- **底を上げても PC の机は救えない**（消灯で点灯時の0.53倍、底×3でも0.63倍。その代わり本棚は点灯時より明るくなる）。PC の机を読めるようにしているのは隣の寒色のネオン

## 自分自身

- **頭は `HEAD_LAYER`。** 視点のカメラと、同じ目に立つ魚眼の立方体カメラは頭を描かない。監視カメラは描く
- **ホログラムの自分は同じ `FigureModel` を `HologramSelf` で描く。** 頭のレイヤーは `Self` だけが付ける（ホログラムの頭は見える）。材質は1つの光の材質に差し替える（髪の `InstancedMesh` のために頂点シェーダーで `instanceMatrix` を掛ける）。装置の上に立たせると右のモニターの陰に隠れたので、前の線画（中心1.45m）と同じ高さに浮かべている
- **体は、どの区画の正面を見ても画面の下の外にある**（デスクトップとスマホの両方、テストあり）。体は首振りにだけ追従し、見上げ・見下ろしでは傾かない
- **監視カメラの映像は、描いているあいだ自分の画面を隠す**（描画先を読みながら書くと WebGL のフィードバックループになる）。毎秒10回に間引いている
- **カーブミラーの反射は本物**（`objects/CurveMirror.tsx`）。鏡の前から部屋を立方体（1面512px、半精度）に描き、鏡面は反射の向きでそれを引く。凸面鏡では反射の光線がほぼ1点から出るので、立方体1つでほぼ正しい（平らな鏡は見る人ごとに鏡の裏からもう1回描く必要がある）。**1フレームに1面ずつ描く**——6面を一度に描くとそのフレームだけ部屋を7回描くことになるので、毎フレーム1回ずつに均した（60fps で毎秒10回の更新）。最初のフレームだけ6面とも描く（半分黒い鏡を見せない）。描くあいだは鏡ごと隠す（監視カメラと同じフィードバックループの理由）。頭（`HEAD_LAYER`）は描く
- **鏡の立方体は半精度でトーンマッピング前の値を持つ。** three.js は描画先へはトーンマッピングしないので、鏡面が画面（または魚眼の面）に描かれるときに一度だけかかる。8bit にするとネオンの1を超える明るさが切れる
- **カーブミラーは、看板を正面に見た標準の画角では右上の角に左端が覗くだけ**（1600px 幅で x 1484〜、中心は1737で画面の外。カードの横寄せで看板の右端がすでに画面の端）。見上げるか魚眼で全体が見える（魚眼ではデスクトップもスマホも縁まで画面内、テストあり）。ユーザーの指定は「看板の右上」で、見え方は確認待ち
- **カーブミラーは下へ傾いて部屋の中央を向くので、上端が壁の側へ倒れる。** 直径96cm では、壁から30cm 出しただけでは裏の上端が壁へ6cm めり込んだ。45cm 出して、裏の縁がどこも壁から2cm 以上離れることをテストで押さえた
- **マーカー（稲妻）は鏡にも監視カメラにも映る**（どちらも同じ層0を描くため）。今は放置している
- **体の部品はポインタを取らない**（`raycast` を空に）。光線は体の中から出る
- **歩数は時間ではなく、目が床の上を動いた距離で数える**（`room/gait.ts`、1ストライド0.9m）。接地した足は体と同じ速さで後ろへ下がるので、どの速さでも滑らない（一歩のあいだのずれ1cm 未満、テストあり）。カメラの姿勢の変化だけから求めるので、飛行・ドラッグ・ホイールのどれが動かしたかを体は知らない。その場で回るのは半径25cmの円を回る距離として数える（足踏み）
- **歩きは「保っている姿勢」（揺れも上下も足す前）から求める。** 目の位置は `forward` から取り、下を向いて目が前へ出る分（`headLean`）を含めない——含めると、下を向くだけで歩き出す。座っているあいだ（`seatShare`）に動いた分は歩数に数えない（椅子ごと寄るときに足踏みしない）
- **歩きの上下（`stepBob`、最大1.5cm、仮）は下がるだけで上がらない。** 足が着く瞬間に一番低い。上がると立った目より上に出て、脚が床に届かなくなる。揺れと同じく描く姿勢にだけ足し、`poseRef` に入れない。座っているあいだと「視差効果を減らす」では0
- **歩く向きを毎フレーム正規化しない。** 正規化すると、前→後ろへ切り替わるときに縮んだ前向きのベクトルが長さ1に戻され、いつまでも前向きのままだった。縮んで0を通り反対へ伸びる（切り返しの途中で足が揃う）
- **座る度合い（`seatShare`）は、目の高さだけでなく「椅子の前にいるか」で決める。** 目の高さだけで決めていたときは、ホログラムの寄り（目1.45m）が0.23「座った」ことになり、手がキーボードへ伸びていた
- **脚は2本の骨（太もも0.37m・すね0.42m、`room/figure.ts` の168cm の体）で、膝はいつも前へ曲がる。** 届かない足は伸びきった脚の先で止まり、床から浮く。脚を伸ばして届かせない（骨の長さが変わる。テストあり）。歩幅は脚に合わせて0.9m（脚0.95m の頃は1.1m）
- **腕も2本の骨（上腕0.32m・前腕0.34m）。** 前は肩から手まで線を引いていただけで、座ると腕が0.75m に伸びていた。キーボードの真ん中は座った目の66cm 前で、168cm の腕では届かない。手はキーボードの手前寄りとマウスの後ろ（`DESK_HANDS`）に置き、座ると肩が6cm 前へ出る。座った視線（`seatedPitch`）は、キーボードではなく手の位置から決める
- **人物の寸法はキャラクターシートから測る**（`room/figure.ts`、正面の立ち姿の画素。地面 y=841、髪の上 y=485）。**カメラの目の高さはそこから決まる**（`EYE_HEIGHT = FIGURE.eye`、1.49m）。股関節はズボンの下で見えないので、横からのウエスト（0.514）と後ろからの股（0.345、腰で穿くズボンで下がっている）のあいだに推定した（0.46）
- **座ると腰から13°前へ傾く**（`SEATED_LEAN`、仮）。人物は頭が大きく脚が短いので、普通の椅子にまっすぐ座ると目が1.35m になる。座った目を1.12m のまま保つと34°の猫背になった。1.20m にして13°の前傾、座面42cm。**座面の高さと椅子の背の位置は体から決まる**（`CHAIR_SEAT_TOP`・`CHAIR_BACK_BEHIND_EYE`）
- **座ったときの足は膝の少し先**（太ももの長さ＋4cm）。最初に机の下へ遠く出したら、膝が座面より低くなり、すねが座面の前の縁を通った（1.7cm）。すねと足が座面に入る深さは、今は歩いて座るまで・立って戻るまでとも入らない（座面の外に2.7cm 以上、テストは1cm 未満を押さえる）
- **髪の帽子は、生え際の形に頂点を寄せて作る**（前は眉の上、横は耳の上、後ろは首まで）。頭は楕円体なので、帽子を傾けて切る形では、後ろや下から見ると頭の丸い下側が肌のまま見えた
- **肌は内側から少し発光させる**（顔は顔の絵を発光の地図にして、目と眉は暗いまま）。部屋の寒色の光の下ではシートの肌色が灰色になった（頬の赤/青の比 1.23。シートは1.76、今は1.80）。手と腕は発光を弱めた（デスクライトの下で白くなった。デスクライトそのものが強いのは照明の段で見直す）
- **PC では、座ったときの椅子の座面が机の前端近くまで入っているので、机と椅子のあいだに立てない。** だから「引いた椅子の前（座る位置から30cm 中央寄り、`ROLL_IN`）に立つ → 座る → 椅子ごと寄る」
- **椅子は、普段は中央から机への通り道の外**（左へ62cm、少し回す。`CHAIR_PARKED`、仮）。最後の50cm を歩くあいだに、まず横に並んだまま下がり、次に背後へ横切る。腰を下ろしながら前へ出て腰の下に入る。立つときは逆。**椅子の位置はカメラの保っている姿勢だけの純粋関数**（`chairPlacement`）で、体と飛行と食い違わない。斜めに一気に横切る形でも今の配置では当たらない（等価な変異）が、歩く人の前を椅子が横切ることになる

## マーカー・点線・カード

- **カードとカメラを相互に更新しない。** 正面の停留所は `facingStop()` が向きから決め、カードはそれを読むだけ（`facingChannel`）
- **カードの送りは「変更」ではなく「要求」。次を受け付ける前に、必ず到着を待つ**（`SectionCard` の `pendingSince`）
- **カードの送りは PC を飛ばす。** PC はカードを持たないので、送りで PC に止まると、送り返すためのカードが無くなる。PC が正面のあいだはカード・点線・レールを出さない
- **マーカーの大きさは画面 px で決め、ワールドの scale を毎フレーム逆算する。** 魚眼では、その位置のレンズの拡大率で（`pixelsPerUnitAt`）
- **マーカーは稲妻の形。点線の切り詰めは必ず `markerClearance()` を通す。** 形・色・寸法比は `scene/markerBolt.ts` に集約
- **点線の起点を、作り直される要素の中に置かない**（`AnimatePresence` が作り直すと、点線が最後の位置で凍る）
- **点線がずれて見えたら、まず「射影がずれている」のか「描き直されていない」のかを分ける**

## React / R3F の境界

- **頻繁に変わる値を `<Canvas>` より上のコンテキストに置かない。購読チャンネルで運ぶ**（`camera/viewChannel.ts`／`camera/markerScreen.ts`／`state/facingChannel.ts`）。R3F 9 の `CanvasImpl` の setup effect には依存配列が無く、再レンダーのたびにシーン全体を再調停する。`React.memo` では止められない。**照明の状態は Context に置いてよい**——切り替えは読み手の操作でしか起きない
- **`frameloop` を切り替えると R3F が `clock.elapsedTime` を0に戻す。** `sceneClock` が単調化を持っている。**自分から動くもの（視点の揺れ、左のモニターの動画、ホログラムの文字の自動再生、マーカーの脈動）は `sceneClock` から時刻を読む**——一時停止で止まる
- **詳細ページがキャンバスを覆っている間は `frameloop="demand"`。**
- **canvas は透明のまま（`<color attach="background">` を足さない）。** 部屋は全画素を覆うが、PC の画面の穴（アルファ0）から後ろの HTML を見せているので、背景色を canvas に入れると穴が塞がる。色は `Hub.tsx` の背景色 div が持つ。**canvas 自身の `pointer-events` は `<Canvas>` の `style` で操作する**（R3F が外側の div にインラインで書くため、祖先の CSS は効かない）

- **マウスの横断面は「親指側の肩」。** 上面はサイドボタンの上の継ぎ目まで続き、そこから側面へ巻き込む（`shoulderAt`）。継ぎ目は真上（6.png）で位置が、真横（10.png）で高さが測れるので、長さの各段で「上面がその場所をその高さで通る」ように左の縁の高さを解く（`leftEdgeAt`、0.95→0.05 と後ろへ下がって親指のくぼみになる）。**全長で同じ横断面にした最初の形は、後ろで継ぎ目が稜線の上に乗り、サイドボタンが真横のシルエットより上に出た**（10.png では高さ82〜94%）。巻き込みを0.72固定にしていた頃は、サイドボタンが真上から幅のある楔に見えた（写真では縁に沿った細い帯）。解いた値は滑らかにつなぐ（`smoothAt`）——折れ線では継ぎ目ごとに陰影が折れた。**サイドボタンの上の縁は、上の殻の左の縁と同じ1本の折れ線**（別々に持っていたら f 0.316 で0.03mm ずれ、割れ目が狭くなった）。**仮の値**: 稜線の位置（前 −0.25 → 後ろ 0、写真から一意に決まらない）、右の縁の高さ0.55、右の巻き込み、ボタンの沈み1.2mm（実物より大きく、椅子から見えるように）、長押しの0.35秒
- **肩の下は親指を置くくぼみ**（2026-10-22 ユーザー「親指が入る窪みがあるはず」、12〜16.png）。肩から凹んで下り、高さの約半分で外へ張り出す翼になり、翼の下は内側へ入って机へ下りる。翼の縁が真上から見た外形。**翼の高さ（`LIP`）は真横（10.png）の、明るいくぼみと翼の下の暗い側面の境目を目で読んだ10点**（f 0.6 で高さの0.45。正面の16.png の0.49と合う）。翼の下の入り込みは正面（16.png）の5mm を、翼が底より立っている高さに比例させる（翼の無い尾の先で入れたら、底が裏返った）。くぼみは「上面の曲線から翼の高さへ、両端で水平につなぐ」だけで凹み、後ろでは翼の縁より低い谷になる（15.png の縁の反り）。**谷を深くする係数（`dip`）を足したが、変異テストで効いていないと分かって外した**
- **横断面の割合は「底から上の分」にだけ掛ける。** 先端では底が机から12mm 浮いているので、全体の高さに掛けると右の縁が底より下に回り込み、殻が折り返した（229面が内を向いた）
- **マウスは机の上を動き、PC の画面のカーソルと一対一に対応する**（`MOUSE_TRAVEL`、マットの上の14cm×7.9cm を画面の 1400×787 に対応させ。縦は画面の比から導く、休む位置が画面の中央）。対応は絶対位置で、相対移動にしない——読み手のポインタを画面に載せる経路と、机のマウスを滑らせる経路の2つでカーソルを動かすので、相対にすると2つがマウスの位置で食い違う。可動域はマット・キーボードの右端・マグから1cm 以上離す（テストあり）。**値の真実は `ExgMouse` の中の目標の位置で、描くカーソル（`ScreenCursor`）と座った右手（`deskHands(mouse)`）は `scene/deskPointer.ts` から表示中の位置を読む**
- **マウスの操作の経路は3つ。** (1) **直接押す**: ボタンは即座に沈んで鳴る。ホイールは押すと沈み、押したまま上下に動かすと回る（1px で0.03rad、仮）。ホイール以外は、どこでも0.35秒動かさずに押し続けると手に持って滑る（持った時点で押していたボタンは離す）。座った構図では手が手のひらを隠し、見えているのはボタンだけなので、**本体だけを長押しの対象にしたら座ったまま持てなかった**。**クリックの判定は上の殻の f 0.5 まで、分かれ目の左右で決める**（2026-10-22 ユーザー「左クリックの判定をもう少し大きく」。前はヒンジ f 0.42 までで、親指側の縁にも届いていなかった）。自由視点では R3F で受けて `pointerClaim` で名乗り、ポインタをつかんでいれば照準で押して移動量で滑らせる。座っているときは canvas がポインタを通すので、window で受けて自分でレイを飛ばす（キーボードと同じ） (2) **読み手のポインタ（マウスが手の届く範囲にあり、PC の画面の上にあるときだけ）**: マウスがその位置へ絶対位置で行き、描いたカーソルがポインタの位置に出て本物の代わりになる（上の「カーソルは1つだけ見せる」「手の届く範囲でだけ操作できる」。2026-10-22 の時点では描いたカーソルを隠していた）。ポインタをつかんでいるとき（位置が無い）は連動しない。**画面の外での相対の連動はしない**——2026-10-22 に「パッド操作に連動して」を「どこでも動きに連動」と読んで入れたが、ユーザーの意図はクリックの連動で、動きの連動は画面の上だけだった (3) **読み手のボタンとホイール（PC の画面の上にあるときだけ）**: 座っているとき、画面の上で押したボタン（`MouseEvent.buttons` の5つ）が同じボタンを押す。画面の上で押し始めたボタンは、ポインタが画面を出ても離すまで押したまま。スクロールも画面の上のときだけホイールを回す（100px で15°）。canvas の上のボタンを押したままのドラッグ（`/lab` の回転）とタッチは連動させない
- **机のマウスを押しているジェスチャのあいだは、読み手のボタンを連動の側に書かない。** 書くと、滑らせる `pointermove` の `buttons` が左ボタンを押したままにし、持った時点の離す音が離したときまで鳴らなかった（ヘッドレスで、再生したクリップの順で見つけた）
- **物が名乗ったジェスチャ（`pointerClaim`）の移動では、視点を回さない**（`Scene.tsx` の `onPointerMove`）。ポインタをつかんだ照準でマウスを滑らせるとき、スマホの指でマウスを滑らせるときに、部屋が一緒に回らないため。キーを押しながら動かしても回らなくなった
- **マウスは本当に割ってある**（2026-10-22 ユーザー「ペイントで線を引いているだけ…オブジェクトとして本当に割って欲しい」、`mouseParts`）。部品は、上の殻（2つのボタンと手のひらが一体、6.png のコントラストを上げて見えた舌の形の輪郭）、その左右の本体、サイドボタン2つ、溝の中の DPI ボタン。上の殻はボタンの分かれ目（前の切り込みから溝まで）と溝で左右に分かれ、溝の後ろでつながる（手のひらは1枚）。尾には継ぎ目が1本。**割れ目は幅0.6mm・深さ1.6mm（仮）の本物のすき間で、壁（暗い色）が殻の内側の暗い面まで下りる。** 深さはボタンの沈みより深い（押したボタンが内側に当たらない）。部品の形は「各行（f）で、その部品が覆う u の範囲」で持ち、全部品が同じ行で切られるので縁がそろう。面の法線は殻の解析的な法線なので、割れていない所（溝の後ろの左右の継ぎ目）は1枚に見える
- **殻は曲率まで滑らかにする**（2026-10-22 ユーザー「表面が少しぼこぼこ、マウスに沿って薄い縞」）。原因は3つあった。(1) 写真の表の1px の段差（±0.5px）——2回の 1-2-1 の平均でならす（`ease`。外形の曲率の向きの入れ替わりが19〜21回→2〜4回） (2) 表を Catmull–Rom（傾きまでしか連続でない）でつないでいて、41段の各標本点で曲率が飛び、2.7mm おきに陰影の縞が出た——3次スプライン（曲率まで連続。解いた値の曲線は両端で水平）にした (3) 稜線の左右の放物線が稜線で曲率を飛ばし、マウスに沿った1本の縞になった。稜線の位置も f 0.35 と 0.6 で折れていた——左右の曲率を稜線の両側0.2で smootherstep で受け渡し、稜線の移動と肩の受け渡しも smootherstep にした。上面の高さの曲率の飛び（2階差分の変化）は長さ方向で 2.6e-5→4.5e-7、横方向で 4.4e-7→3e-8（テストあり）。写真から解いた左の縁の高さも1回ならす（10.png の列ごとの読みで 0.47→0.05→0.12 と跳んでいた）ので、継ぎ目の高さは写真の値の1mm 以内（前は厳密）
- **角は丸い**（2026-10-22 ユーザー「角が尖りすぎ」、17〜19.png）。(1) 割れ目の縁: 部品の面を、縁の手前 `ROUND.edge`（0.5mm、仮）から4分の1円で割れ目へ落とし、法線を縁の外へ傾ける（縁ごとに3列・3行を足す）。細くなる部品では、届く幅を帯の4分の1までにして半径も縮める (2) 翼の縁: `ROUND.lip`（1.2mm、仮、翼が低い所はその半分の高さまで）で丸めて下へ向け、その下の側面は垂直に始まる（`sin²` で入り込み、机でも垂直） (3) 足元: 右の壁と翼の下の側面が机に接する所を `ROUND.foot`（1mm、仮）で内へ丸め、底はその内側から。**先端では足元を丸めない**（高さが0の行全体が内へずれて折り返した）
- **向きの検査の例外は2つ、理由つき**: 部品が幅0へ細る先端（f < 0.03・> 0.98。前は上の殻の脇の本体、尾は継ぎ目が壁から抜ける所）の1mm² 以下の数枚と、真横を向いた面（余弦 ±0.05 以内。サイドボタンの穴の前の縁で、本体の端が1行で跳ぶ段差）。段差の手前に0.01mm の行を足して面にしようとしたら、真横の面と壁が23枚に増えたので戻した
- **割れ目の幅は面に沿って測る**（`gapAt`、u 方向の弧長で換算）。上から見た横幅で換算していた最初の形では、肩の下の急な側面（4mm の横幅で25mm 下る）で割れ目が約6倍の3.7mm に開き、暗い帯に見えた。溝の穴は上から見た寸法なので横幅のまま
- **割れ目の壁は、1枚ごとに両端の法線の平均の向きへ押し下げる。** 端ごとの法線で押すと、曲がりのきつい所（サイドボタンの前端、前と尾の先）で2つの端が交差し、四角形がねじれて半分が裏返った
- **内側の暗い面（`inside`）は殻を内へ押した面で、割れ目と溝からしか見えない。** 前の丸み（半径が深さより小さい）では浅くし（0.5mm から）、先端の1.5%ずつは張らない（潰れた先端から押すと折り返す）。**翼の縁から1.5mm 内側までにする**——縁から真下に押すと、翼の下で内へ入る側面より外に出て、暗い筋が見えるはずだった。肩のきつい曲がりでは内側の面が折り返すが、殻の中に収まる（テストあり）ので、向きの検査からは外した
