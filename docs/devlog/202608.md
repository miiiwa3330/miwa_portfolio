### 太陽オブジェクトを置いて、読み手が動かせるようにする

- 仕様は先に決めた: **太陽を直接ドラッグ** ／ **置いた場所に止まる（自動では動かない）** ／ **全周自由・制限なし** ／ **夜側は環境光を上げて底を作る** ／ **光るスプライト**。
- **「置いた場所に止まる」が効くのは、惑星のほうが回り続けるから。** カメラ追従版が失敗した原因は「陰影が変わらないこと」だったので、太陽を止めても惑星がツアーで回る以上、陰影は常に変化し続ける——失った半分だけを取り戻す形になっている。
- **光源と見た目の太陽は、同じ方向の別々の半径にある。** directional light は向きしか意味を持たず、`position` は影カメラがそこに置かれるという理由でだけ効くので、光は `SUN_DISTANCE`（41）から動かせない。見た目のほうは自由。
- **最初 `SUN_SPRITE_DISTANCE = 260`（カメラの最遠到達点の外）に置いたら、一周して一度も画面に映らなかった。** 理由は幾何: **カメラは常に惑星の中心を見ているので、視野は「その1方向まわりの約33°×22.5°の円錐」しかない。** 遠くの物体はほぼ自分自身の方向に見えるので、その円錐に入るには惑星のほぼ真裏にいる必要があり、そこでは惑星に隠れる。実測でツアー6点中0点。
  - **近づけると幾何が反転する**（惑星の円盤の**脇**に見えるようになり、そこには余白がある）。`SUN_ORB_RADIUS = 34` に決定——地表に立つもの全部（`SCENE_BOUNDING_RADIUS`）の外で、自由回転の最も近い高度（`NEAR_ORBIT_RADIUS` 50）の内側。裏に回れば惑星が隠すので「日が沈む」も成立する。ツアー6点中2点で可視（右上、約350px）。
  - **大きさは画面pxで持ち、毎フレーム world scale を逆算する**（`markerScaleForScreenRadius`、マーカーと同じ）。半径34だとカメラからの距離が一周で16〜84まで振れるので、world scale 固定だと5倍に膨らむ。掴む対象なので、一周を通して同じ大きさである必要がある。
- **一度は「カメラ側に回ったらフェードで消す」を入れたが、指示により撤去した**（「太陽は、見えなくなる必要はない」）。街の上に光点が乗る状態は仕様として受け入れる。
- **代わりに「俯瞰モードのときだけ太陽が出て、動かせる」ことにした**（指示）。**これが発見性の問題も同時に解いた**——標準（半径50）では惑星の円盤が19.7°を占めるうえ `NEAR_VERTICAL_SHARE` で右下に寄っているため、太陽は画面の角に切れて一周の約1/3しか映らなかった。俯瞰（半径100）なら円盤は9.7°で、空の余白が広い。**光そのものは止まらない**——置いた場所から、どの高度でも、セクションに寄っている間も照らし続ける。
- **ドラッグは「差分ぶん回す」ではなく「ポインタから球へレイを飛ばして、その点に置く」。** 最初は差分回転（1pxあたり `fov / viewportHeight` ラジアン）で書いたが、**実測で追従率41%**だった。原因は幾何で、修正可能な係数のズレではない: 半径34の球を外から見ていると、太陽は円周の大部分で**視線に沿って**動いていて画面上ではほとんど動かない（カメラに正対する位置で運動の94.7%が視線方向）。必要な補正係数は定数ではなく、**シルエットで無限大に発散する**。球との交点を取れば係数そのものが要らなくなる——**実測で追従率100%**（ポインタ286px→太陽287px）。
  - **常に手前側の交点を採る。** つまり1回のドラッグで届くのはカメラに面した半球まで。裏側はツアーが勝手に回してくれるので、回ってから掴み直せば届く。シルエットを越えたら奥側の交点へ飛び移る（いわゆるアークボール）方式は、端までドラッグしただけのつもりの手で太陽が裏へワープするので採らなかった。
  - 外れたレイには**シルエット上の最も近い点**を返す。返さないと、手が行き過ぎた瞬間に太陽が固まる。
  - 惑星の回転ドラッグとは `sunDraggingRef` で排他——R3F のポインタイベントは canvas で先に発火し、`useViewInput` は `window` で後から受けるので、フラグは必ず間に合う。

### 太陽をカメラと一緒に動かす案——実装して計測して、見た目で却下

- **発端**: 「現状ライトは、惑星に対して固定になっていますか？」→ はい、という確認から、「カメラ自身を光源（太陽）として捉える考え方もあるなと思いました。どうですか？」という提案。まず**その案が解こうとしている問題が実在するか**を測るところから始めた。
- **問題は実在した。しかも固定光では原理的に解けなかった。** これは今後も効く結論なので残す。
  - 旧・主光源 `[18, 34, 14]` に対する各エリアの入射: skills 21.7°（明るさ1.96）／ experience 69.6°（1.31）／ products 64.7°（1.09）／ about 138.9°（0.73）／ **contact 142.2°（0.27）**。contact は skills の**7分の1**で、ツアーはそこを通り、カードはそのエリアを説明するのに建物はほとんど見えていなかった。
  - **太陽の向きを全球総当たり（2°刻み、16,200通り）しても、「最も暗いエリア」を 0.000 より上げられる向きは存在しない。** 5つのアンカーは球面上で **149.5°** に散らばっており、どの方向から照らしても必ず1つはターミネーターの向こうに落ちる。**定数の調整では解けない。**
- **「カメラ＝光源」そのもの（θ=0）は最初から採らなかった。** 視線と光軸が一致するとボクセルの立体感が消え、影が自分の裏に落ちて見えなくなり、惑星がスタジオの球に見える。代わりに**視線軸から `SUN_TILT` ずらした主光源**を実装した。角度は実測で決めた: 正面エリアはカメラ方向から**中央値18.1°・最大40.1°**ずれる（円盤の中心ではなく5アンカーの最近傍なので）／ツアー一周での「正面エリアの N·L 最悪値」は 20°→0.565・28.6°→0.455・40°→0.292・60°→0.000 ／ 一方 **19.6°未満だと可視円盤が丸ごと明部に入りターミネーターが画面に出ない**。28.6°（ロール34°）に決定。
- **明るさの目的は達成した。** contact のツアー位置で、惑星が占める領域の**平均輝度 62.1 → 120.7（1.94倍）**。
- **それでもユーザー判断で却下。「あまり良くなかった」「ぼやぼやしている」。**
- **「ぼやぼやするのは繰り返し描画しているからか？」という問いには、はっきり No と答えられた。** 一時停止ボタンでカメラ（＝この仕様では光源も）を止め、**5秒あけて2枚撮ると完全に同一**（平均差 0.00、8以上変化した画素 0.00%）。時間方向のちらつきは無い。白飛びも 0.00%。
- **本当の原因は「影が減ること」だった。** 光が視線軸から28.6°しか離れていないと、各建物の影が自分の裏に隠れる。砂地（単色なので濃淡が全部陰影と影）で測ると、**影と判定された面積が 26.9% → 20.6%（-23%）**、影の深さも下位10%輝度が 84.7 → 89.3 と浅くなっていた。**しかも計測したのは固定光でも明るい側の位置**で、暗い側ではもっと差が出る。
  - 加えて数字にしにくい要素として、**光がスクリーンに固定されるので、惑星が回っても陰影が一切変わらない**。ツアーを回る楽しさの一部が消える。
  - **全体の標準偏差（sd 35.0 vs 35.2）や局所コントラスト（4.66 vs 4.65）では差が出なかった**——地形と建物の固有色の変化が支配的で、陰影の差が埋もれる。**単色領域を選んで測って初めて見えた。** 「コントラストを測る」ときに何を測っているかを取り違えた例として残しておく。
- **残したもの**: `scene/sunLight.ts` は残し、中身を**光源の距離と影のフラスタムの関係**だけに絞った（`SUN_DISTANCE` / `SCENE_BOUNDING_RADIUS` / `SUN_SHADOW_NEAR` / `SUN_SHADOW_FAR` / `SUN_DIRECTION` / `sunPosition()` / `incidence()`）。これは太陽をどこに置く仕様になっても共通で効く不変条件で、以前は `Scene.tsx` の JSX にリテラルで散らばっていて**関係そのものを書き下せなかった**。テストで「影のフラスタムがシーンを内包する」ことを押さえてある——外すと、影のカメラが world を depth range から外して**影が黙って描かれなくなる**。
- **次**: 「太陽オブジェクトを置いて、ユーザーが光源の位置を自由に変更できる」案へ。ドラッグ中以外は固定光なので、今回の「影が減る」問題は起きない。

## 2026-08-05

### カメラの切り替わりがカクつく——原因は3つ、いずれも「値が飛ぶ」バグだった

- **報告**: 「詳細ページからホームに戻るときや自己紹介からホームに戻る時など、カメラが変わるたびに、カメラの挙動がカクついたりしている」。まず全遷移を洗い出してから直す方針にした。
- **カメラの行き先を決めているのは `Scene.tsx` の effect ひとつ・分岐7つで、そこから生まれる遷移は13通りあった。** 初回マウント／ホーム→セクション／ホーム→About／セクション→ホーム（スクロールで抜ける・HOME・ロゴ）／自由回転→ホーム（ロゴ）／About→ホーム（読み切り・ロゴ）／ズーム段階の変更／URL・ブラウザバック／セクション→別セクション／ドラッグ復帰／ホイール・スワイプ／ポーズ。**問題があったのはこのうち5通りで、fps ではなく値の不連続が原因だった。**

**① 飛行が着地したあと、次のフレームでカメラが巻き戻る（セクション→ホーム、ロゴ→ホーム）**

- `flyToOrbit` は `azimuthTargetRef`／`polarTargetRef` しか書かず、飛行中は frame loop が早期 return するので `azimuthRef`／`polarRef` は**飛行前の値のまま凍る**。着地は `glideRef.current = null` にするだけで、再同期が無かった。
- 次のアイドルフレームは `current = azimuthRef`（飛行前）から damp を始める。60fps では `1 - exp(-5/60) = 0.080`、つまり**ギャップの92%を1フレームで巻き戻して**から0.6秒かけて戻り直す。
- 巻き戻る量はセクション→ホームで**最大36°**（開いた瞬間にそのエリアのアンカーからどれだけ離れていたか＝**開くタイミング次第でランダム**。これが「たまにカクつく」の正体）、ロゴ→ホームで**最大180°**。
- **これは `CLAUDE.md` が About について書いている失敗そのもの**（「着地後の `damp` が数十度を引き戻すワープになる」）。About だけ `azimuthRef` を毎フレーム書いて解決済みで、分岐3・5には同じ手当てが入っていなかった。
- **直し方**: 飛行を `scene/cameraFlight.ts` という純粋モジュールへ切り出し、飛行レコードに `land`（着地後に自由回転が引き継ぐ角度。自由回転へ降りる飛行だけが持ち、セクション／About への飛行は `null`）を持たせた。`advanceFlight` は着地フレームだけ `landed` を返し、`Scene.tsx` がそれで `azimuthRef`／`polarRef`／両ターゲットの4本を揃えてから `glideRef` を落とす。飛行中 `tourURef` は凍っているので、着地値と次フレームが再導出する目標は一致し、残差ゼロで damp に引き継がれる。
- **About と違って「移動する着地点」にはしなかった。** 飛行1.6秒ぶんのツアー前進は `0.032 × 1.6 = 0.051 rad`（2.9°）で、`easeInOutCubic` が速度0で着地したあと damp が滑らかに拾う範囲。About が移動点を必要としたのは旅の長さがスクロール量に依存して数十秒に及びうるため。

**② `frameloop` を切り替えるとシーン時計が0に戻り、世界が飛ぶ**

- `frameloop={obscured ? "demand" : "always"}` が変わると、R3F 9.6.1 の `setFrameloop` が `clock.stop(); clock.elapsedTime = 0; clock.start(); clock.elapsedTime = 0` を実行する（`events-*.esm.js:1087`）。`sceneClock.time(elapsed)` は `elapsed` が単調である前提だったので、**詳細ページを開くたび・閉じるたびに時刻が過去へ飛ぶ**。
- 巻き添え: 路面電車（位置が時刻の関数なのでワープ）、雲4体、住人5体、マーカーのパルス・`boltFlicker`・`strikeIndex`（点線が引き直される）。
- **一番目立つのはスペーサへスクロールし始めた瞬間**。`Hub.tsx` の `setCovered(progress <= 0)` は progress がわずかでも立てば `false` を投げるので、**スペーサが透けて惑星が見えている状態で**リセットが起きる。
- 二次被害として、ポーズを使ったことがあると `skipped > 0` のまま時刻が負になり、`ScenePause` は `[paused, clock]` でしか再実行されないのでポーズと再開の間にリセットが挟まると `skipped` が恒久的に壊れる。
- **直し方**: `sceneClock` に単調化を1層入れた（`restarts` に巻き戻り幅を積む）。`frameloop` の切り替え自体は省電力のために残す。`setPaused` も同じ `now()` を通す——ここを素の `elapsed` のままにすると、リスタート後にポーズを押した瞬間に40秒ぶんの時刻が捨てられる。

**③ About の復帰カメラがスクロール位置の生値そのままだった**

- `t = easeInOutCubic(aboutReturn.progress())` は scroll イベントで publish された値をそのまま使い、ホイールハンドラは `element.scrollTop += wheelScrollStep(...)` と**即時に加算**していた。トラックパッドのフリックは大きく不規則な delta を吐くので、**カメラがホイールイベントの粒度でそのまま段階的に動く**。自動再生で読んでいるあいだだけ滑らかで、手で加速した瞬間にカクつく。
- **直し方（採用: スクロール自体を平滑化）**: ホイールは目標 `scrollTop` だけを動かし、既存の rAF ループが実 `scrollTop` をそこへ寄せる（`scrollCatchUp`、λ=12＝約0.25秒）。`t` の定義が変わらないので着地精度もそのまま。文字の流れ自体も滑らかになり、クロールとして本来こちらが正しい。カメラ側だけ damp する案は、文字が跳んでカメラが遅れて追う二重の動きになるので採らなかった。
- 目標は自前の数なので `scrollTop` のような自動クランプが無く、`clampScroll` で両端に留めている（無いと overscroll が貯まって「スクロールが効かない」に化ける）。**2つの時計を使い分けた**——自動再生はシーンの時計（ポーズで止まる）、寄せは実時間（ポーズ中にホイールを回しても届く。`Scene.tsx` の飛行が実 delta を使うのと同じ理由）。

**ついでに直したコスト系（②③と同じ「遷移の瞬間に重なる」もの）**

- **`AppStateContext` の `facing` を購読チャンネル（`state/facingChannel.ts`）へ移した。** これは1ラップに5回変わる値で、変わるたび `Hub` → `<Canvas>` が再レンダーし、R3F 9 の `CanvasImpl` の setup effect には**依存配列が無い**ため `configure()` と `root.render()` がシーン全体（惑星・5棟・`FillerCity` 290棟・装飾一式）を毎回再調停していた。
  - **`React.memo` では止められない**、と分かったのが今回の収穫。`its-fine` の `useContextMap`（R3F がコンテキストをリコンサイラ境界の向こうへ運ぶ仕組み）は `CanvasImpl` のレンダー中に上位の全コンテキストを `use()` で購読するので、props が変わらなくても Canvas は再レンダーする。しかも memo すると今度は `CameraController` が `activeSection` の変化を受け取れなくなる（Bridge は `root.render` 経由でしか値を運ばない）。**打てる手は「Canvas より上のコンテキストが変わる回数を減らす」しかない。**

### 点線もジグザグをやめて稲妻に——波形だけ捨てて、不変条件は3つとも残す

- **要望**: 「点線自体も稲妻のようにして欲しいです。今のジグザグデザインは、捨てて大丈夫です」。確認したうえで、**形はマーカーの火花と同じ拍で引き直す**・**枝分かれを出す**の2点を決めて着手した。

- **最初の実装は稲妻に見えなかった。原因は「平均回帰する歩行」を選んだこと。** `lift = 0.45·前 + 0.55·目標` という凸結合にすれば「しばらく同じ向きに走ってから鋭く折れる」感じが出る、と考えたが、**凸結合は中央へ引っ張る**ので定常のばらつきが ±2.5px 程度にしかならず、13px 刻みに対して**ゆるく波打つ線**にしかならなかった（ヘッドレスのスクショで一目瞭然だった）。稲妻を作るのは**左右への切り返し**のほうで、`RUN_CHANCE = 0.25` で時々同じ側を続けるのが「鋸歯にしない」ための味付け。刻みも 13→26px、振れ幅も 7→10px に上げた。

### エリアのマーカーを水色の稲妻に——円をやめた瞬間に「半径ひとつ」が破綻する

- **要望**: 「マーカーのデザインを変えて欲しいです。稲妻のイメージのマーカーにして欲しいです。水色の稲妻です」。形・色・点線の扱い・動きの4点を確認して着手した（回答: 定番のZ字ボルト／通常も正面も水色で正面は発光／点線とカード隅のドットも水色に揃える／正面のマーカーだけ時々パチッと光る）。

- **近似を2つ試して2つとも捨てた。**
  - **内接楕円（半軸 0.52 × 1）は安全ですらなかった。** 上の先端 (0.30, -1.00) は楕円の**外**にある——(0.30/0.52)² + 1 = 1.33——ので、先端付近では点線を稲妻の上に描いてしまう。「楕円なら円の自然な一般化だから安全」という直感が、実際に数字を入れると成り立っていなかった。
  - **凸包の支持関数は安全だが緩い。** 頂点の射影の最大を取る方式は真の輪郭より必ず外側なので食い込まないが、**真下方向で実際のインクの1.67倍**を返す（インクは 0.598 で終わるのに 1.00 を返す）。方向によって隙間が9pxから15px近くまで変わる＝呼吸する隙間の言い換えでしかない。
  - **採ったのは厳密解**: 中心からレイを飛ばして輪郭との交点を取る（`markerClearance()`）。6辺しかないので毎フレーム呼んでも無視できる。
- **`markerClearance` が1つの数を返せるのは、この輪郭が中心について星形だから。** 実測したところ **20000方向のうち19999で前方交点はちょうど1つ**（残り1つは頂点をかすめたレイの重複カウント）。実装は max を取る形で書いてあるが、**それは星形でなくなったときにも壊れないためであって、いま効いているわけではない**。最初この理由を「切り欠きに騙されないため」と書いたが、変異テスト（max→最初の交点）が**通ってしまった**ので調べ直して分かった——**意味的に等価な変異で、テストの穴ではない**。docstring のほうを事実に合わせ、代わりに星形であること自体をテストで固定した（中心から外へ歩いてインクの区間が1本だけであることを見る。腰の頂点を折り返す変異で赤くなることを確認済み）。

### カード上のスクロールが「効いたり効かなかったり」——正体は慣性テールが次のフリックを飲んでいたこと

- **報告**: 「カードの上にカーソルを合わせている時のスクロールの感度が悪いです。カードが切り替えれたりできなかったりするので、適切に切り替えられるようにしてください。ですが、次のカード出現していないのに、その次のカードに切り替えられるようなことは防いで下さい」。**要望が2つ入っていて、素直に読むと逆を向いている**——「もっと反応してほしい」と「先へ行きすぎないでほしい」。同じ1つのつまみ（しきい値）で両方は満たせないので、**別々の欠陥として切り分けるところから始めた。**
- **主因は `cardWheel.ts` のロック解除条件が「静止」しかなかったこと。** 「1ジェスチャ＝1枚」は、しきい値を越えた瞬間に `locked` を立て、`GESTURE_GAP_MS`(220ms) の静止でだけ解く、という形で実装されていた。ところが **macOS のトラックパッドの慣性テールは1〜2秒 wheel を吐き続ける**。テールが走っている最中に指を戻して2回目のフリックをすると、そのイベント列はテールとの間隔が220ms未満なので新しいジェスチャとして認識されず、**2回目のフリックが1発残らず捨てられていた**。テールが切れたあとに出せば効く——**効いたり効かなかったりの分かれ目は「前のテールに重なったかどうか」で、読み手からは完全にランダムに見える。** これが報告の症状そのものだった。
- **テールと「指が戻ってきたこと」は、大きさの推移で見分けられる。** 慣性テールは単調に減衰するのに対し、駆動されている列は大きくなる。そこで「**このジェスチャの山の半分を下回ってから（`REARM_DECAY_SHARE = 0.5`）、直前のイベントの2.5倍以上に跳ね上がった（`REARM_RISE = 2.5`）**」を、静止と並ぶ2つ目の解除条件にした。**フリック自身の立ち上がり（2→5→13→34→88→240 のような急上昇）で誤爆しないのは、上昇中は「直前のイベント＝山そのもの」で減衰の条件が成立しないため**——この2条件は片方だけでは意味を持たない。
- **`REARM_FLOOR`（「これより小さいイベントでは再武装しない」下限）を一度は入れたが、落とした。** テールの末端では 2.5 倍が丸め誤差でも成立しうる、というのが理由だったが、**それが実害になるシナリオを書けなかった**——深いテールで再武装しても、残っている移動量は数十しかなく80に届かない。**「壊れたときに何が起きるか」をテストで書けない定数は、根拠のない定数**なので、`REARM_RISE = 2.5` だけで整数のゆらぎ（2→3、1→2）は弾けることを確認して外した。仮に幻の再武装が起きても、後述の到着ゲートが二重の受け皿になる。
- **もう1つの要望「次のカードが出ていないのにその次へ」は、しきい値ではなく到着ゲートで構造的に禁じた**（`AreaCard.tsx`）。**ステップは「変更」ではなく「要求」である**——`onStep` は `turnRequest` を投げるだけで、`section` が返ってくるのはカメラが damp で振れて別のアンカーが最近傍になったあと。**ここを待たないと2つ同時に壊れる**: (1) `Hub.tsx` の `adjacentOnTour(card, step)` に**退場中のカード**を渡すことになり、同じセクションを指して**スクロールが空振りする**、(2) 空振りしなかったときは、出そろっていないカードを飛び越す。`pendingSince` を立て、**`section` が変わったことだけを到着の合図に**して降ろす。
- **待ち時間は目測ではなく実装から導いた。** カメラ側は `ORBIT_DAMP_LAMBDA = 5` で、アンカー間隔1.27 radに対し境界は0.6 rad（47%）なので `1-e^(-5t)=0.47` → **約0.13秒**。カード側は登場スプリング（stiffness 420 / damping 38 / mass 0.7）が ζ≈1.11 のわずかな過減衰で、遅い極の時定数が約64ms → **160ms で9割方その場にいる**。合わせて**最短約0.3秒＝毎秒3枚**。`STEP_TIMEOUT_MS = 1000`（damp が1秒で残差1%を切ることから）は要求が届かなかったとき用の保険で、通常経路では踏まない。
- **ゲートに弾かれたジェスチャは、そこで打ち止めにする（accumulator を生かさない）。** 拒否のたびに移動量を溜めておくと、**ゲートが開いた瞬間に、もう誰も駆動していないテールが次の1枚を買ってしまう**。読み手が本当に次を求めているなら、次の新しいジェスチャで必ず通る。
- **`deltaY` を `deltaMode` で正規化する `wheelPixels()` も足した。** Chrome はマウス1ノッチを100px（px モード）、Firefox は同じ1ノッチを3行（行モード）で寄越す。しきい値80に対して「1ノッチ＝3」では**27ノッチ必要**で、硬いのではなく死んでいる。`LINE_PX = 33` は**行の実高ではなく、Chrome のノッチと一致させる値**——しきい値が校正されている相手がノッチのほうだから。
- **`WHEEL_THRESHOLD = 80` は据え置いた（ユーザー判断）。** 50 に下げる案（マウス1ノッチの半分＝軽い2本指スワイプでも確実に1枚）を提示したが「80のまま」を選択。**取りこぼしの主因が慣性テールの誤判定だと切り分けられていたので、しきい値を触らずに直せた**——最初に感度のつまみを回していたら、誤爆を増やしただけで本当の原因は残っていた。
- **`Hub.tsx` と `Scene.tsx` は1行も触っていない。** 到着ゲートが「ステップを受け付けた時点で `card` は必ず最新」を保証するので、`adjacentOnTour` に渡す値の問題は Hub を触らずに閉じる。スワイプ（`useCardGestures`）も同じ `takeStep` を通るため、**ロックが一切無かった素早い連続スワイプの空振りも同時に塞がった。**

- **検証**: `npm test` **369件（+8）**・`tsc`・`lint`・`build` すべてクリーン。
  - **変異テスト5種すべてが、狙ったテスト1つだけを落とした**（`cp` で退避→当てる→`cp` で復帰）: `climbing → false` で「テールに重なった2回目のフリック」、`REARM_RISE 2.5 → 1.0` で「揺らぎながら減衰するテール」、`decayed` の条件を外すと「フリック自身の立ち上がり」、`LINE_PX 33 → 1` で行モードの2件、`PAGE_PX 400 → 3` でページモードの1件。

- **要望**: 「自己紹介文の文字一つ一つの配置について、`reference/image9.jpg`のように、綺麗に一列にする方法はありますか？」。**寸法・角度・サイズは何度も image9 に合わせてきたのに、文字組みだけを一度も参考写真に照らしていなかった**——本文は `text-center` ＋ ブラウザ任せの折り返しで、幅・禁則・字送りに指定が一切無く、左右ともギザギザだった。

### 惑星への復路を早める——`ABOUT_RETURN_FROM` を 0.5→0.35

- **要望**: 「もう少し早い段階から惑星へのズームが始まるようにしてほしい」。復路は飛行ではなくスクロールが握っていて、その開始点が `ABOUT_RETURN_FROM`。読了約110秒に対して、開始が約55秒地点→約38秒地点になる。
- **値は0.35。** 「もう少し」に対する調整幅は、このプロジェクトの前例（自動スクロールを「もう少し遅く」で3割落とした）に合わせて3割減とした。さらに早めるのは定数1つで済むので、体感で足りなければ動かせる。

### 自己紹介からの帰りをツアー経路に乗せ、消え際を厳密化し、影を撤去

### 自由回転を離したあとの復帰を、自動回転と同じ速度域まで落とす

- **要望**: 「長押し＋スライドで惑星を自由回転できますが、自動回転と同じくらいのスピードでデフォルト軌道に戻ってください。現状早すぎます」。
- **原因は「速度ではなく時間で戻していた」こと。** 復帰は `THREE.MathUtils.damp(current, target, 5, delta)` 2本で、damp は残差の**割合**（`1 - exp(-λΔt)`）を毎フレーム詰める指数減衰なので、**距離が変わっても所要時間はほぼ半秒で一定**。つまり大きくドラッグするほど速く引き戻される——「惑星を手からもぎ取られる」感触の正体で、`AUTO_ORBIT_SPEED`（0.032 rad/s）とは一桁違っていた。
- **damp を捨てずに「速度の上限」を被せた。** `MathUtils.damp` は `1 - exp(-λΔt)` を係数にした lerp そのものなので、**係数を1つ計算して方位・極角の両方に掛ければ damp 2本と完全に等価**（`orbitStepFraction()`）。そのうえで `min(damped, maxArc·Δt / arc)` を取れば、同じ経路のまま速度だけが頭打ちになる。ここで `arc` は方位差でも極角差でもなく**大円の弧**（`orbitArcBetween()`）——方位1radが実際に横切る距離は `sin(polar)` 倍なので、方位で上限を書くと極に近いほど速く走れてしまう。
- **上限は `ORBIT_RETURN_SPEED = AUTO_ORBIT_SPEED × 2`。等倍にはできない。** 復帰中も `tourURef` は前進し続けるので、**目標そのものが `AUTO_ORBIT_SPEED` で逃げている**。等倍だと真後ろから追う最悪ケースで接近速度が0になり永久に着かない（テストで `Infinity` として固定した）。2倍なら最悪ケースの**接近速度がちょうど `AUTO_ORBIT_SPEED`**、横から寄る場合で2倍——どちらも自動回転と同じオーダーで、要望どおり「スナップ」ではなくなる。
- **上限を掛けるのは「離したあとの復帰」だけで、ホイールとカードのスワイプには掛けない。** どちらも読み手が今まさに要求した移動で、0.4 rad のフリックに6秒かけたら**入力が無視されたようにしか見えない**。`returningRef` という明示的なモード（ドラッグを離した瞬間に立ち、次の `pointerdown`／ホイール／`turnRequest`／飛行の開始で降りる）で切り分けた。**「今の差分の大きさ」では区別できない**——ホイールで飛んだ直後と、ドラッグを離した直後は、どちらも同じだけ経路から離れているため。
- **復帰の終わりに閾値を持たせなかった。** 上限は残り `speed/λ ≒ 0.013 rad` あたりで damp より緩くなり、そこから先は damp が勝つ。**「上限が効かなくなったこと」自体を到着とみなす**（`fraction >= damped` でフラグを降ろす）ので、独立したしきい値を後から同期し続ける必要がない。最後の0.7°はイージングで収まる。
- **`AUTO_ORBIT_SPEED` を `Scene.tsx` から `worldLayout.ts` へ移した。** 定数を参照する定数ができた以上ローカルではないうえ、「復帰速度はアイドル速度を上回らなければならない」という不変条件は、両方が import できて初めてテストに書ける。
- **検証**: `npm test` 362件（+16）・`tsc`・`lint` クリーン。変異は5種（復帰速度20倍／上限を外す／弧の式の sin・cos 入れ替え／上限から `delta` を落とす／復帰速度を等倍）を当て、それぞれ2〜8件が赤化することを確認（退避は `cp`、`git checkout` は使わない）。**ヘッドレスに一時的な計測用フックを仕込んで実測した**（計測後に撤去）: 極角を +0.28 rad ドラッグして離すと、復帰中の実測速度は**0.0640 rad/s で一定**、`returning` が降りたあとは**0.0319 rad/s**（＝`AUTO_ORBIT_SPEED`）へそのまま連続。所要**約4.7秒**。同じ操作を上限なし（`Infinity`）で走らせると**最初の0.5秒の平均で0.2475 rad/s**、1サンプル目にはもう到着済み——変更前後がそれぞれ「自動回転の8倍」「2倍」であることを数字で確認した。

### 二本指ズームが効かなかった原因はScene.tsx側ではなく、ブラウザのネイティブなピンチズームだった

- **報告**: 「二本指でズームができていません」。`Scene.tsx`の`useViewInput`には`pinchStartDist`/`PINCH_THRESHOLD_PX`を使ったピンチ検出が既にあり、`onPinchZoom("near"/"far")`が`AppStateContext`の`setOrbitZoom`まで正しく配線されていた——ロジック自体は壊れていなかった。

### 自己紹介を自動再生に、ペースを遅く

- **要望**: 「何も触らなくても、自動で流れるようにして。スクロールのスピードを遅くして」。ここまでの自己紹介は完全にホイール駆動で、開いても何もしなければ`scrollTop=0`のまま止まっていた。
- **`useFrame`が使えない。** Aboutはキャンバスの外側にあるプレーンなDOM要素で、R3Fのフレームコールバックの外にいる——`scene/*.tsx`の自走物（観覧車・トラム・住人）はみな`useFrame`経由で`sceneClock.delta(delta)`を読んでいるが、同じ手は使えない。代わりに自前で`requestAnimationFrame`ループを張り、`performance.now()`の差分を実時間の`delta`として`sceneClock.delta()`に渡す形にした——`sceneClock`自体はReactやR3Fに依存しない素の関数なので、呼び出し元がR3Fの内か外かは問わない。CLAUDE.mdの「自分から動くものはsceneClockから時刻を読む」を、Canvasの外の自走物にも初めて適用した形。
- **`aboutScroll.ts`に`autoScrollStep(deltaSeconds)`を追加し、既存の関数群と同じく純粋関数として置いた。** `ABOUT_AUTO_SCROLL_SPEED`（px/秒）を掛けるだけの単純な式だが、`Scene.tsx`の`MAX_FLIGHT_STEP`と同じ理由で1フレームあたりの最大値をクランプしてある——バックグラウンドタブから復帰した直後の`requestAnimationFrame`は数秒分のギャップを持って来ることがあり、それをそのまま`scrollTop`に加算すると行を飛ばして進んだり`ABOUT_RETURN_AT`を一気に超えて画面が閉じたりしかねない。
- **「スクロールのスピードを遅くして」は、比較対象になる「前」の実装が無かった（今回が初めての自動再生実装）ので、最初から遅めの値（22px/秒）を選んだ。** 全文を読み切るのに1分半〜2分半程度かかる計算——実写のオープニングロール（60〜90秒程度）よりやや長いくらいで、「急いで流れる」印象にはならないはずという判断。ホイール（`wheelScrollStep`）は残したままなので、自動再生に任せず自分のペースで読みたい・読み返したい場合はそちらが効く。
- **ヘッドレスでは速度そのものを検証できなかった。** 素の`requestAnimationFrame`の発火間隔を測ると、`--disable-background-timer-throttling`等のフラグを足しても3秒間で4回（約1.1fps）しか呼ばれない——CLAUDE.mdが警告する「SwiftShaderはページ全体を毎秒3フレーム程度まで落とす」の直接の帰結で、Aboutのループもこの主スレッドの詰まりの影響を受ける。実測した`px/秒`はどう足掻いても意図した22px/秒には遠く及ばなかったが、これは**実装のバグではなく計測環境の限界**と判断した根拠は3つ: (1) `autoScrollStep`の単体テストは実時間の`deltaSeconds`を直接渡しており、環境のfpsに依存しない——ここが正しければ実機の60fpsでも同じ式で正しい値が出る、(2) 素のrAF発火間隔を計測しても同程度まで落ちており、Aboutのコード固有の問題ではない、(3) 一時停止ボタンを押すと`scrollTop`が6秒間ぴったり0px動かず、再開すると再び動き出すことを確認できた——ロジックの結線自体は機能している。**体感のペースは実機で確認してもらうしかない**、とだけ記録しておく。
- **新規テストは`autoScrollStep`に3件追加し、変異テストで検証した。** `cp`でスクラッチパッドへ退避してから、(a) クランプを外す変異、(b) 速度定数を22→10にする変異の2つを別々に当て、両方とも対応するテストが赤くなることを確認してから`cp`で復元した。
- **検証**: `npm test`329件（+3）・`tsc`・`lint`・`build`すべてクリーン。ヘッドレスで、①ホイールを一切送らずに`scrollTop`が時間とともに増えていくこと、②一時停止で止まり再開で動き出すことの2点を確認した（速度の絶対値はヘッドレスでは測れないため対象外）。

### 配置をもっと左へ、自動スクロールをさらに遅く

- **要望**: 「左の文字列が画面左面にかかるくらいのバランスに配置してください。また、自己紹介自動スクロールをもう少し遅くしてください」。前回`left-[15%]`→`left-[8%]`まで寄せていたが、それでもまだ手前の広い行は画面左端に届いていなかった——右側は惑星に重なるくらい伸びているのに対して非対称だった。
- **`HubDock.tsx`の`left-[8%]`を`left-[-3%]`まで踏み込んだ。** 本文が`text-center`（中央寄せ）である以上、列の左端そのものを画面外まで出さないと、中央に寄る文字は画面端に触れない——8%（正の値、画面内）では届かないと分かったので、負の値まで動かした。
- **`ABOUT_AUTO_SCROLL_SPEED`を22→14px/秒に下げた。** 「もう少し」という言葉どおり、大きく削るのではなく3割程度落とす調整にした。
- **検証**: 見た目のみの変更で、`autoScrollStep`のテストは期待値をリテラルのまま新しい速度（0.7・1.4）に更新——構造は変えていないため変異テストは前回のものを流用できる（クランプの有無・速度定数の変更という2種の変異は前回すでに検証済み）。`npm test`329件（件数不変、期待値更新のみ）・`tsc`・`lint`・`build`すべてクリーン。ヘッドレスで、手前の広い行が画面左端に触れる位置まで来ていること、`scrollTop=0`が変わらず空であることを確認した。速度の体感は前回と同じ理由（SwiftShaderのフレームレート低下）でヘッドレスでは測れないため、実機での確認待ち。

### 「自動スクロールがされなくなっている」——正体は冒頭の空白と速度の組み合わせ

- **報告**: 「自動スクロールがされなくなっているので、直してください」。コンソールエラー無し、`scrollTop`はヘッドレスでも確かに時間とともに増えており、一時停止ボタンの状態も正常——ロジックそのものは壊れていなかった。
- **原因は冒頭の空白（`h-full`≒900px）と、直前の変更で下げた速度（14px/秒）の組み合わせだった。** 900px ÷ 14px/秒 ≈ 64秒——見出しが画面に現れ始めるまで1分以上かかる計算になっていた。この空白はもともとホイール駆動が前提の頃に「上にスクロールするまで画面外に」という要望で入れたもので、その後「自動再生」「もう少し遅く」を重ねた結果、この空白を抜けるだけで1分以上かかる設計になっていたと気づいた。数十秒待って何も動かなければ「動いていない」と判断するのは当然で、実装のバグではなく設計の見落としだった。
- **`About.tsx`の冒頭の空白を`h-full`→`h-[8%]`（約72px）に縮めて直した。** 空白のサイズは画面の高さではなく自動再生の速度に対して決めるべき値だった、という位置づけの変更。
- **ユーザーから「何をしているのか、単に定数を変えるだけではないか、落ち着いて」という指摘があった。** 実際には定数（`ABOUT_AUTO_SCROLL_SPEED`）は一切触っておらず、空白のクラス名1箇所とその周辺のコメントだけの変更だったが、調査の過程で複数のヘッドレススクリプトを走らせていたため大掛かりに見えたのだと判断——変更箇所が小さいことと、それが今回の症状の直接の原因であることを短く伝えて収めた。
- **検証**: `npm test`329件・`tsc`・`lint`すべてクリーン。ヘッドレスで、ページ読み込み直後の短い待ち時間だけで見出しがすでに視界に入り始めていること（`h2`の`offsetTop`が新しい空白サイズと整合すること）を確認した。

### 「配置と速度、この指示の前まで戻れますか」——直前2件の変更を差し戻し

- **要望**: 「『左の文字列が画面左面にかかるくらいのバランスに配置してください。また、自己紹介自動スクロールをもう少し遅くしてください』この指示をした前まで戻れますか？」。指定された指示が原因で追加した2つの変更——`HubDock.tsx`の`left-[8%]`→`left-[-3%]`と、`ABOUT_AUTO_SCROLL_SPEED`の22→14——を名指しで差し戻す依頼。
