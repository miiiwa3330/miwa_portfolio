- **3Dモデルは「コードで手続き生成」。** 外部の GLB を読む案・骨格はコードで装飾だけ GLB の案もあった。コードで組めば配置を純関数に持ててテストでき、アセットの制作手順を新しく決める必要も無い。Blockbench の MCP ワークフローはボクセル専用なので、どちらにしても引き継げない

- **設計の中心: モジュールを中心から放射状に張り出させれば、カメラの仕組みは作り直さずに済む。** 今のカメラが惑星について知っているのは「セクションが中心から見てどの方向か」「その方向を上とする接線基底」「中心からの距離（`sectionGroundRadius(section)`）」の3つだけだった。地面を前提にしているのは土台・雑居ビル・プラザ・バス・雲の側だけで、カメラ・ツアー・マーカー・カード・スマホ・About の仕組みはどれもこの3つしか読んでいない
  - `sectionGroundRadius()` は、定数を返すだけなのに `section` 引数を残してあった（docstring に「次の土台が方向で変わらない約束ではない」）。**ここがモジュールごとの距離の違い＝増築の乱雑さの入り口になる**
  - 乱雑さは**方向ではなく距離・大きさ・ひねり・トラスで出す。** 方向はツアーの縛り（緯度±60、経度順、隣の緯度を近づける）を守る必要があるので散らせない

### `sandbox/room-lab.html` で部屋の試作を作り、魚眼の3方式を見比べた

### ズームは「物へ近づく」に変更。魚眼の2方式の違いを説明した

- **ユーザー**: ズームは「物へ近づく」に変更。魚眼の樽型2種の違いが分からない
- **ズーム**: 試作の初期値も「物へ近づく」に戻した。これで「カメラは3段階とも中央から動かない」（直前の節）は取り消し——**中央を離れるのはズームのときだけ**で、今のサイトの「建物へ寄る→戻る」と同じ形になる
- **魚眼の説明**: 150°の比較（前の節）では2方式がほぼ見分けられなかったので、161°と210°で PC を正面にして撮り直してから説明した。どちらも「正面からの角度」を「画面の中心からの距離」に写すが、**立体射影**（r ∝ tan(θ/2)）は縦横の比率を保つので端の物の形が崩れず、代わりに正面が小さめ・端が大きめになる。**等距離射影**（r ∝ θ）は正面が大きめで、端の物が横に押しつぶされる
  - 161°の計算値: 正面の倍率は等距離が立体の **1.21倍**（2·tan(H/2)/H、H は水平画角の半分）。画面の左右の端で、等距離は横方向（円周の向き）に対して径の方向が **0.70倍**に縮む（立体は1倍）。210°では正面の倍率の比が **1.42倍**に開く。撮った画像でも、等距離は正面の机が大きく、右端の展示棚が細くなっていた
  - Claude は、部屋を見渡す用途では端の家具の形が崩れない立体射影を勧めた。正面の PC を大きく見せたいなら、等距離にするか、立体射影のまま画角を狭める
- **踏んだ罠**: 1回目の撮影のあとに確認用のサーバーを `kill $(cat server.pid)` で止めたつもりが、控えた PID は `( ... & echo $! )` のサブシェルのもので、`python3 -m http.server` 本体（別の PID）が残っていた。`lsof -ti:8765 -sTCP:LISTEN` で本体を見つけて PID 指定で止めた。**`&` で起動するときは、サブシェルで包まずに `$!` を取る**

### HTML を3Dの中に置く方式を試作で確かめた。PC は「後ろ＋穴あけ」、ホログラムは「手前に重ねる」

- **狙い**: 要件で、PC の画面とホログラムの文字は「部屋の中の3Dの物として存在する HTML」になった。ここが成り立たないと要件を見直すことになるので、設計の最初に確かめた。`sandbox/room-lab.html` に `CSS3DRenderer` で2つの置き方を足し、隠れ方を見るために机の前に椅子とデスクライト（照明の要件の物）を置いた
- **結果**: 「手前に重ねる」は透けるが、手前の物に隠れない（椅子の背もたれの上に画面のタスクバーがはみ出した）。「後ろに置いて穴をあける」は隠れるが、穴の向こうが HTML の層の背景なのでホログラムが黒い板になった。**PC は後者、ホログラムは前者**。クリックは両方で届き、本物のマウスクリックでアイコン→ウィンドウ→×で閉じる、までを確かめた
- **踏んだ罠 ①（長かった）: 3Dの変換がかかった要素に `overflow: hidden` があると、Chrome は当たり判定を一切返さない。** 見た目は正しいのにクリックが届かず、`elementFromPoint` を格子状に投げて数えながら切り分けた。縮尺（0.0005倍→1000倍の空間）・遠近の入れ方（関数→プロパティ）・`pointer-events` はどれも0点のまま。遠近を外すと134点、変換を全部外すと485点。最小構成で足し引きして、**単純な値で252点が `overflow: hidden` で0点**と特定した。画面とウィンドウから外して解決（本文の `overflow-y: auto` は無害だった）
- **踏んだ罠 ②: ズームの立ち位置を、物の正面ではなく背面（壁側）からの距離で計算していた。** 家具は「ローカル +Z が中心向き」で置いているので、正面は中心からの距離 `dist - d/2`。`dist + d/2` と書いていて、奥行きのぶんだけ寄りすぎていた（最初の試作の「ボードがはみ出した」にも一部効いていたはず）
- **踏んだ罠 ③: 立った目の高さのまま PC に寄ると、画面を29°見下ろして文字が台形に歪んだ。** 座った高さ（1.12m）まで下げて正面から向き合わせた。寄る距離も、机全体（2.1m）ではなく中央の画面（0.62m）を基準にした——机全体だと本文22pxが約6pxになって読めない
- **樽型の魚眼の段では HTML を出さない**（CSS は通常の遠近しか描けず、歪んだ部屋と合わない）。魚眼の段の画面は貼った絵になり、開いたウィンドウなどの今の状態は映らない
- **踏んだ罠 ④: バックグラウンドのサーバーの PID をサブシェルで取って、止め損ねた。** `docs/verification.md` に書き足した

- **ユーザーの質問「なぜ three.js に頼らないの？」に答えた。** 描画は three.js のまま。計算だけを切り離すのは、(1) テストが WebGL 無しの Node で2秒未満で回る (2) 試作で踏んだ「正面と背面の取り違え」のような、画面には何か映るので気づきにくい誤りを仕様のままテストに書ける (3) three.js の部品へ変換する場所を1か所に絞れる、から。three.js のベクトル計算自体は Node でも動くので「three.js を使うとテストできない」わけではない、とも伝えた
- **設計からの変更: `buildTour()` を再利用しなかった。** 経度が増える向きが部屋の中から見ると左で、そのままだとナビの順と逆に巡る。首振りの角度そのものを経路上の位置にした水平な輪にした。`Tour` 型は同じなので `Scene.tsx` からの使い方は変わらない
- **家具を3.3mに合わせて置き直した。** 試作の寸法のままだと机と作業台が1.6°重なっていた。机・通信端末・扉・作業台の角度と幅を変え、隙間を3°以上にした
- **調査ボードは中央からでも画面の約75%を占める**（7割に収めるには約3.1m要るが、中央からボードまで約2.9m）。ズームは中央に留まる。対処は見た目の段階で判断する
- **踏んだ罠**: (1) 隙間のテストを `% 360` で丸めていて、1.6°の重なりを「358.4°の隙間」として通していた。Python の手計算で気づいた (2) `vitest run --root /` がファイルシステム全体を走査し始め、`pkill -f` でも止まらず PID 指定の `kill -9` で止めた
- **変異テスト18種が全部落ちた**（一覧は `docs/room-migration.md` の「手順1の結果」）

### 手順2: トップの3Dを惑星から部屋に差し替えた

- **何が変わったか**: カメラは部屋の中央に立って首を振り、セクションを選ぶとその物の正面へ寄って戻る。カード・マーカー・点線・巡回・ズームの段・スマホのカードレールが6か所の停留所で動く。家具と照明は仮の形（試作と同じ程度）。詳細は `docs/room-migration.md` の「手順2の結果」
- **カメラ制御の書き換えで、残したものと外したもの**: 入力の判定（ドラッグ・ホイール・2本指・ピンチ・タップ）、ドラッグ後の速度つきの復帰、行き先を決める effect が1つ、飛行の2つの約束（最初のフレームに時間を加えない・着地で角度を引き継ぐ）は残した。`camera-controls`、建物ごとのカメラの「上」、横寄せのためにカメラを動かす仕組み、自己紹介のスクロールでカメラを引く分岐、建物の出現を待ってやり直す仕組み（`pendingFocusRef`）、ウィンドウの大きさが変わったときに組み直す effect は外した——どれも惑星に固有の問題への対処だった
- **向きの値は首振り・見上げで持ち、減衰の関数（`orbitStepFraction`）は方位角・極角として渡して再利用した。** 大円の弧で測る関数なので、首振り＝方位角、見上げ＝極角の余角で同じ意味になる
- **カードを避ける横寄せは、投影の中心をずらす方式（`setViewOffset`）に。** 画面の幅に対する割合なので、リサイズで組み直す処理が要らない
- **実装の中で決めたこと**: カードの送りは PC を飛ばす（PC はカードを持たない）。ホイールを下へ回すと右を向く（＝ナビの順に進む。惑星では逆向きだった）
- **踏んだ罠**: (1) 椅子の背もたれ（高さ1.19m）がホームの画面の真ん中を塞いだ。中央から PC の画面の下端への視線は、椅子の位置で床から約1.07mを通るので、0.98mに下げた。試作は中央から PC を見る構図を撮っていなかった (2) React の lint がフックから受け取ったカメラへの書き込みを止めた。カメラは `useFrame` の引数から受け取る形に (3) ヘッドレスで `h3` を読むと SEO 用の見えない見出しを拾った（`verification.md` に追記）
- **確認**: ヘッドレスで PC とスマホ幅の主な流れを撮った（ユーザーの `next dev` を閲覧だけで使った）。テスト591件（+17）・`tsc`・`lint` が通り、新しい純粋関数への変異10種が全部落ちた
- **仮の状態のまま残したもの**: 魚眼は画角を120°に広げるだけ（手順3）、スマホの縦の画角が約110°（手順3）、自己紹介はクロールを手前に重ねる（手順5）、照明は仮（手順6）
