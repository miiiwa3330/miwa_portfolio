  - `sectionGroundRadius()` は、定数を返すだけなのに `section` 引数を残してあった（docstring に「次の土台が方向で変わらない約束ではない」）。**ここがモジュールごとの距離の違い＝増築の乱雑さの入り口になる**
  - 乱雑さは**方向ではなく距離・大きさ・ひねり・トラスで出す。** 方向はツアーの縛り（緯度±60、経度順、隣の緯度を近づける）を守る必要があるので散らせない

### ズームは「物へ近づく」に変更。魚眼の2方式の違いを説明した

- **ユーザー**: ズームは「物へ近づく」に変更。魚眼の樽型2種の違いが分からない
- **ズーム**: 試作の初期値も「物へ近づく」に戻した。これで「カメラは3段階とも中央から動かない」（直前の節）は取り消し——**中央を離れるのはズームのときだけ**で、今のサイトの「建物へ寄る→戻る」と同じ形になる
- **魚眼の説明**: 150°の比較（前の節）では2方式がほぼ見分けられなかったので、161°と210°で PC を正面にして撮り直してから説明した。どちらも「正面からの角度」を「画面の中心からの距離」に写すが、**立体射影**（r ∝ tan(θ/2)）は縦横の比率を保つので端の物の形が崩れず、代わりに正面が小さめ・端が大きめになる。**等距離射影**（r ∝ θ）は正面が大きめで、端の物が横に押しつぶされる
  - 161°の計算値: 正面の倍率は等距離が立体の **1.21倍**（2·tan(H/2)/H、H は水平画角の半分）。画面の左右の端で、等距離は横方向（円周の向き）に対して径の方向が **0.70倍**に縮む（立体は1倍）。210°では正面の倍率の比が **1.42倍**に開く。撮った画像でも、等距離は正面の机が大きく、右端の展示棚が細くなっていた
  - Claude は、部屋を見渡す用途では端の家具の形が崩れない立体射影を勧めた。正面の PC を大きく見せたいなら、等距離にするか、立体射影のまま画角を狭める
- **踏んだ罠**: 1回目の撮影のあとに確認用のサーバーを `kill $(cat server.pid)` で止めたつもりが、控えた PID は `( ... & echo $! )` のサブシェルのもので、`python3 -m http.server` 本体（別の PID）が残っていた。`lsof -ti:8765 -sTCP:LISTEN` で本体を見つけて PID 指定で止めた。**`&` で起動するときは、サブシェルで包まずに `$!` を取る**

### HTML を3Dの中に置く方式を試作で確かめた。PC は「後ろ＋穴あけ」、ホログラムは「手前に重ねる」

- **狙い**: 要件で、PC の画面とホログラムの文字は「部屋の中の3Dの物として存在する HTML」になった。ここが成り立たないと要件を見直すことになるので、設計の最初に確かめた。`sandbox/room-lab.html` に `CSS3DRenderer` で2つの置き方を足し、隠れ方を見るために机の前に椅子とデスクライト（照明の要件の物）を置いた
- **結果**: 「手前に重ねる」は透けるが、手前の物に隠れない（椅子の背もたれの上に画面のタスクバーがはみ出した）。「後ろに置いて穴をあける」は隠れるが、穴の向こうが HTML の層の背景なのでホログラムが黒い板になった。**PC は後者、ホログラムは前者**。クリックは両方で届き、本物のマウスクリックでアイコン→ウィンドウ→×で閉じる、までを確かめた
- **踏んだ罠 ①（長かった）: 3Dの変換がかかった要素に `overflow: hidden` があると、Chrome は当たり判定を一切返さない。** 見た目は正しいのにクリックが届かず、`elementFromPoint` を格子状に投げて数えながら切り分けた。縮尺（0.0005倍→1000倍の空間）・遠近の入れ方（関数→プロパティ）・`pointer-events` はどれも0点のまま。遠近を外すと134点、変換を全部外すと485点。最小構成で足し引きして、**単純な値で252点が `overflow: hidden` で0点**と特定した。画面とウィンドウから外して解決（本文の `overflow-y: auto` は無害だった）
- **踏んだ罠 ②: ズームの立ち位置を、物の正面ではなく背面（壁側）からの距離で計算していた。** 家具は「ローカル +Z が中心向き」で置いているので、正面は中心からの距離 `dist - d/2`。`dist + d/2` と書いていて、奥行きのぶんだけ寄りすぎていた（最初の試作の「ボードがはみ出した」にも一部効いていたはず）
- **踏んだ罠 ③: 立った目の高さのまま PC に寄ると、画面を29°見下ろして文字が台形に歪んだ。** 座った高さ（1.12m）まで下げて正面から向き合わせた。寄る距離も、机全体（2.1m）ではなく中央の画面（0.62m）を基準にした——机全体だと本文22pxが約6pxになって読めない
- **樽型の魚眼の段では HTML を出さない**（CSS は通常の遠近しか描けず、歪んだ部屋と合わない）。魚眼の段の画面は貼った絵になり、開いたウィンドウなどの今の状態は映らない
- **踏んだ罠 ④: バックグラウンドのサーバーの PID をサブシェルで取って、止め損ねた。** `docs/verification.md` に書き足した

### 手順3: 視点の3段。樽型の魚眼を本体に入れ、マーカーとクリックも同じレンズの式で求めた

- **レンズを1本の式にした**: `r = tan(θ/k) / tan(H/k)`（`scene/camera/fisheye.ts`）。k=1 が通常の遠近、k=2 が立体射影。**どの k でも画面の左右の端が水平画角 H の位置に来る**ので、標準（k=1・67°）から魚眼（k=2・161°）への飛行で k と画角を一緒に補間すると、部屋が飛行のあいだに曲がっていき、最後の1フレームでレンズが入れ替わることが無い（引き継ぎで出ていた案をそのまま採った）
- **描画**: 魚眼のあいだ（k が1より少しでも大きいあいだ）だけ、`CubeCamera` で立ち位置から6方向を描き、全画面の板のシェーダーで画素ごとに視線の向きを引く（試作 `sandbox/room-lab.html` と同じ）。`useFrame` に優先度1を付けて R3F の描画を乗っ取り、k=1 なら普通に `gl.render` する（`scene/LensRenderer.tsx`）。立方体の面は1辺1024px（スマホは512px）の半精度。**値は仮**で、実機の速さを測ってから決める
- **確かめ方: k=1 のまま立方体を経由して描かせ、直接の描画と画素を比べた。** 6点とも色まで一致した（横寄せ0.22のずらし込み）。シェーダーの式・ずらし・トーンマッピングと色空間の扱いが、three.js の通常の描画と同じだと言える。比べるための一時的な切り替えは外した
- **マーカーの位置と大きさ、クリックの当たり判定も同じ式で求める。** 画面上の位置は `projectToScreen`、大きさは `lensPixelsPerRadian`（k=1 では「焦点距離÷奥行き」＝three.js がスプライトを描く大きさそのもの）、クリックは R3F の `events` の `compute` を差し替えて `screenRay`（`projectToScreen` の逆）で光線を飛ばす。**対照として差し替えを外すと、魚眼の段でマーカーに一度も当たらなかった**（点線の終端から40pxの範囲でホバー0回。差し替えありでは1歩目で当たり、ホログラムへ寄った）
- **見つけた不具合: カメラの毎フレームの処理が、マーカーの処理より後に走っていた。** R3F の `useFrame` は同じ優先度なら登録順に走り、部屋（とその中のマーカー）が `CameraController` より先にマウントされている。マーカーは前のフレームのカメラで射影し、描画は今のカメラで行うので、**首を振っているあいだ点線の先が1フレーム遅れる**——`scene-invariants.md` の「`useFrame` の中でカメラの行列を読む前に `updateMatrixWorld()`」が防ごうとしていたのと同じ症状が、別の経路で起きていた（手順2で `camera-controls` を外したときに入った）。カメラの `useFrame` を優先度 -1 にして先に走らせた（負の優先度は描画を乗っ取らない）
- **スマホの画角を別の定数にした（どちらも仮）**: 標準は**縦78°**（390×844 で横約41°）。デスクトップの横67°をそのまま使うと縦約110°で天井が画面の3分の1を占めていた。縦で決めたのは、縦長の画面では縦が長い辺で、天井と床がどれだけ入るかを決めるから。70°・78°・86°で撮り比べ、70°は展示棚の右が切れ、86°は天井が増えたので間を取った。魚眼は**横90°**（立体射影で縦約168°）。デスクトップの161°をスマホに使うと縦が約245°になり、真上と真下を越えて部屋が折り返す
- **スマホでは被写体を上へずらす（仮）**: 下のカードレールが画面の下を塞ぐので、投影の中心を縦にずらす（`projectionShiftPx` の縦版 `projectionLiftPx`）。量は「カードレールの上の帯の真ん中」で、レールの上端の実測664px（844px中）から `1 − 664/844 = 0.21`。惑星では逆に下げていた（水平線を入れるため）が、部屋には水平線が無く、レールが隠すのは床
- **却下した案**: スマホの魚眼をデスクトップと同じ161°にする（上のとおり縦が180°を超えて折り返す）。魚眼の段だけ横寄せ（カード）をやめる（カードは魚眼でも出るので、ずらしをシェーダーに入れて両方の段で同じにした）
- **テスト**: 610件（+19）。変異19種が全部落ちた（一覧は `docs/room-migration.md` の「手順3の結果」）

### 手順5: 自己紹介をホログラムに。クロールとスクロールでカメラを引く帰り道を外した

### 手順7: 自分自身。体・頭の出し分け・監視カメラ・手・映り込み

- **できたこと（見た目はすべて仮）**: 視点のカメラの位置に、フードをかぶった簡単な人の形（円柱と球）が立つ。首振りに合わせて向き、見上げても体は傾かない。**頭だけ three.js のレイヤー1**に置き、視点のカメラと魚眼の立方体カメラ（同じ目の位置）には描かせない。右のモニターには、壁の上の監視カメラから部屋を毎秒10回描いた映像が映り、中央に立つ自分（頭も）が映る。PC に座ると腰が椅子の座面に、手がキーボードとマウスに乗る。丸窓のガラスに薄い人影の絵

- **原因**: 立方体の面を `CubeCamera.update` で直接描いていたので、アンチエイリアスが無かった。しかも面は1024px 固定で、画素比2では魚眼の画面の中心で約1.85倍に引き伸ばされていた
- **直し方**: 面ごとに MSAA 4倍の作業用の描画先（半精度）へ描き、トーンマッピングしながら 8bit sRGB の立方体へ写す。面の大きさは画面の幅と画素比から決める（上限1536px、スマホ1024px、仮）。8bit にしたのはメモリ（半精度の立方体の半分）のためで、ネオンのように1を超える明るさが切れないよう、トーンマッピングは写す段で済ませる（three.js は画面に描くときしかトーンマッピングしないので、ACES を写すシェーダーに一字一句写した）。ビデオメモリは約170MB（スマホ約75MB）
- **確かめ方**: k=1 のまま立方体を経由して描かせて直接の描画と比べる（手順3と同じ）。今回は点だけでなく**差分の画像**も作った
- **見つけた不具合: 魚眼で床が机の手前に描かれていた。** 差分の画像の下端に暗い多角形の帯（輝度10.7、直接の描画は24.0）。変更前の描き方でも同じ値で、手順3からあった。体を隠しても変わらず、床を隠すと消えた。帯の上端の多角形は床の円の縁。**立方体の面のカメラは部屋の軸にそろっていて、床の円の中心の頂点（カメラの真下）がその平面上（w=0）に乗る**のが原因と見て、床と天井を奇数（9）に分割した正方形の板に替えたら揃った（25.3 対 25.6）。原因の見立ては、直ったことから逆に推したもので、w=0 の頂点がこの絵を作る仕組みまでは確かめていない
- **踏んだ罠**: 手順3の「6点の色が一致」は、どの点も画面の下端に無く、この不具合を素通りしていた（`verification.md` に追記）

### 「リアル化の順序」と「WebGL の描き方」の相談

- **ユーザーの問い**: 大枠を作ってから最後にリアルにするか、最初から1つずつ質を上げて作るか。Claude の答えは「大枠 → 1区画で見た目の方針（照明・材質・後処理）と描画の予算を決め切る → 全体へ広げる → 個別の作り込み」。理由は、写実感は照明と材質という部屋全体にかかるもので決まるので、物を先に作り込むと照明を変えたときに調整がやり直しになること。それから、魚眼が1フレームに6回描くので、影や SSAO の重さが何倍にも効き、先に予算を決めないと作り込んだものを削ることになること。**ユーザーの決定はまだ無い**（記録だけ）
- **2DのUI・オブジェクト・視点は別物として考えてよいか**: 作業は分けられるが、境目が3つある。(1) オブジェクトと視点は `layout.ts` の寸法でつながる (2) 後処理を入れるならレンズ（立方体の面ごとか、曲げたあとか）とトーンマッピングの写しに効く (3) PC の画面は canvas の穴（アルファ0）から見せているので、アルファを潰す後処理は穴を塞ぐ
- **体は視点に合わせて動いているのか**: 動いている（毎フレーム、カメラの姿勢から関節を置き直していた）。ただ、揺れが小さく、体そのものの動き（歩く・重心）が無いので、止まって見える。動かしても描画の負荷はほとんど変わらない（どうせ毎フレーム全部描き直している）。効くのは影を入れたとき（動く物は影を焼き込めない）

### 歩いて座る。視点の人が、カメラの移動に合わせて歩き、PC では椅子に座る

- **ユーザーの指示**: 「視点に合わせて人物自体が歩くようにしたい。PC にズームしているときは椅子に座るようにしたい」。その次に「何も操作していないときは、その人が自由に動き回る」、さらに「ハンモックに寝て本を読むなどの要素を追加していけるように」。**今回は1つ目だけ**
- **歩数は時間ではなく距離で数える**（`room/gait.ts`）。1ストライド（左右2歩）＝1.1m（仮）。接地している足は、体が進むのとちょうど同じ速さで体の後ろへ下がるので、どの速さでも床を滑らない。時間で歩かせると、飛行が加速・減速するたびに足が滑る。カメラの姿勢の変化から歩きを求めるので、飛行・ドラッグ・ホイールのどれが動かしたかを体は知らなくてよい。その場で回るときも、足が半径25cmの円を回る距離として数え、足踏みになる
- **飛行を「歩く」形にした**（`camera/walkFlight.ts`）。今までは全体を1本のイージングで滑らせていたので、最高速が平均の1.875倍になっていた（1.9m を1.1秒で、瞬間に約3.2m/s）。歩きでは、0.35秒で加速、1.5m/s（仮）で巡航、0.35秒で止まる。区画への飛行の長さ（行きと帰りで同じ）: PC 2.70秒（前は1.1秒）、ホログラム 1.57秒、スキル 1.32秒、連絡先 1.31秒。制作実績（1.0m）は1.1秒より短く歩けるが、1.1秒に合わせて遅く歩く。経歴は中央から動かないので今までどおりの滑らか
- **カメラに歩きの上下を足した**（最大1.5cm 下がる、仮）。足が着く瞬間（両足が床にある瞬間）に一番低く、片足の真ん中で元の高さ。**下がるだけで上がらない**——上がると立った目の高さより上に出て、脚が床に届かない。揺れと同じく描く姿勢にだけ足し、飛行の起点（`poseRef`）には入れない。OS の「視差効果を減らす」では0、座っているあいだも0
- **PC の座り方**: 座ったときの椅子は、座面の前端が机の前端（2cm手前）まで差し込まれていて、**人が机と椅子のあいだに立つ隙間が無い**。そこで「引いた椅子の前に立つ → 腰を下ろす → 椅子ごと30cm 机へ寄る」にした（`ROLL_IN`、仮）。座るのは0.8秒、寄るのは0.45秒（どちらも仮）
- **椅子の置き場を、中央から机への通り道の外にした。** 引いた椅子の位置は通り道の上にある。最初に考えたのは、椅子を机の左右に寄せておき座るときに横から入れる形だったが、立っている脚を横切ることになる。決めた形は、普段は左へ62cm 寄せて少し回した位置（`CHAIR_PARKED`）。最後の50cm を歩くあいだに、まず椅子が下がり（横に並んだまま）、次に背後へ横切って回り込む（`CHAIR_APPROACH`）。腰を下ろしながら前へ出て、腰の下に入る。立つときは逆に、立ちながら後ろへ押し出され、離れながら脇へ戻る。椅子の位置も体の関節も**カメラの姿勢だけから決まる純粋関数**（`room/seat.ts` の `chairPlacement`）で、飛行と食い違わない
- **椅子が脚にぶつからないことを測った**: PC へ歩いて座るまで、立って中央へ戻るまでを1/120秒刻みで追い、すねと足が椅子の座面の中へ入る深さの最大を測った。歩いて座る5mm、立って戻る3mm（ふくらはぎが座面の縁に触れる程度）。テストで1cm 未満を押さえた
- **ついでに解消した「確認待ち #30」**: 中央から見ると椅子が手前に大きく写る件。椅子が普段は脇に寄っているので、中央から PC を見ても画面の真ん中には来なくなった
- **見つけて直した不具合: ホログラムの前で、手がキーボードへ4分の1ほど伸びていた。** 座る度合いを目の高さだけで決めていた（1.55m→1.12m）ので、ホログラムの寄り（1.45m）で0.23「座った」ことになっていた。座る度合いは「椅子の前にいるとき」だけにした（`seatShare`）。ホログラムでは膝を曲げて目を下げる

### マウスの見回しを、ドラッグから FPS ゲームのような照準に替えた

- **ユーザー**: 「視点の方向を、長押しスライドではなく、FPSゲームのようにエイムの方向に視点が向くようにしてみて」
- **作り方: Pointer Lock API。** カーソルが画面の端で止まると、そこから先へ回れない。ロックすればカーソルの位置ではなく移動量（`movementX`/`movementY`）が来るので、何周でも回れる。部屋を1回クリックするとつかみ（対象は canvas）、Esc で返す（Esc はブラウザが持っているキーで、ページからは変えられない）。ロックはユーザーの操作の中からしか取れないので、自動ではつかまない
- **向きは減衰させない。** 今までのドラッグは目標を動かし、描く角度は λ=5 で追いかけていた（隙間が約0.2秒で縮む）。照準が手から遅れるのはゲームでは「重い」ので、保っている角度にそのまま足す。目標にも同じ量を足すので、ホイールの滑りの途中で動かしても、滑りの残りは消えない
- **向きの符号はゲームと同じ**（右へ動かすと右を向く、上へ動かすと上を向く）。指のドラッグの「世界を掴む」（2026-10-01 のユーザーの決定）とは逆向きになる。スマホの指のドラッグは今までどおり残した。感度は0.002 rad/px（ドラッグと同じ値、仮）で、1440px の画面を端から端まで動かすと約165°。生の移動量（`unadjustedMovement`）は使わず、OS のマウス・トラックパッドの速さの設定が効く CSS px で読む——Mac のトラックパッドで生の値がどう来るかを確かめられないので、読み手が自分で合わせた設定を活かす側にした
- **つかんでいるあいだのクリックは照準を撃つ。** ロック中のブラウザはイベントの座標をロックした瞬間の位置に止めるので、R3F の光線はそこから出続ける。`roomEvents` の `compute` で、ロック中は照準の位置（`aimPoint`）から光線を出すようにした。**照準は画面の中央ではない。** デスクトップの自由視点はカードを避けて投影を横へずらしている（`ORBIT_CARD_SHARE` 0.22）ので、視線の軸は幅の61%（1600px 幅で x=976）。照準の点も、当たり判定も、同じ `projectToScreen([0,0,-1])` から取る
- **区画に寄ったらカーソルを返す。** 寄った先のカード・PC の画面・詳細ページはカーソルで読むので。戻ってきても自動ではつかみ直さない（上のとおり、ブラウザがユーザーの操作を要る）
- **マーカーとスイッチのクリックは、つかむ前でもそれらのもの。** つかむ処理は `window` の `pointerdown` で、R3F の物の `onPointerDown` が先に `pointerClaim` で名乗るので、それを見て譲る
- **案内**: つかんだ直後の2.5秒だけ、照準の下に「Esc でカーソルを戻す」を出す
- **確かめたこと**（ヘッドレス、1600×900）: 壁をクリック → `pointerLockElement` が canvas、照準の点が x=976 に出る。マウスを右へ300px → 机から展示棚へ右を向いた。照準を机のマーカーに合わせて（上へ86px）クリック → `#desk` へ寄って座り、ロックが外れた。つかんだまま机の壁をクリック → 何も起きずにつかんだまま。**Esc は確かめられていない**——ヘッドレスでは CDP のキー入力がブラウザのロック解除に届かず、Esc のあともロックが残った（実機の Chrome ではブラウザ自身が解除する）。1回だけ、最初のクリックでロックが取れなかった実行があった。同じ手順を3回繰り返したら3回とも取れて、再現しなかった
- **テスト**: 432件（+4）。`mouseLook`（右へ動かすと右を向く、`viewDirection` の外積で向きを確かめる／上へ動かすと上を向く／1px あたりの量／見上げ・見下ろしの上限で止まり、上限の先に値を溜めない）。変異3種（左右の符号・上下の符号・上限なし）が全部落ちた。`MAX_PITCH` は `Scene.tsx` から `cameraMotion.ts` へ移した（純関数とカメラで同じ数を2か所に持たない）

### 照準を画面の中央の◯にした

- **ユーザー**: 「エイムは画面中央に配置してください。エイムのUIは◯にして」
- **前の照準は視線の軸の上だった**（幅の61%）。デスクトップの自由視点は、左のカードを避けるために投影を右へずらしている（`ORBIT_CARD_SHARE` 0.22）ので、軸が中央より右にある。中央に置くと、照準は軸の約12°左を見る（`atan(0.22 × tan45°)` = 12.4°）
- **案は2つあった**: (a) 照準と当たり判定を中央に置き、投影のずらしはそのまま (b) つかんでいるあいだは投影のずらしを0にして、軸を中央へ戻す。(b) はつかむ・離すたびに部屋が幅の11%ぶん横へ動き、カードの横に物を出すという今の構図も崩れるので、(a) にした
- **(a) で踏んだもの: カードが照準と違う物を出した。** ヘッドレスで照準を机のマーカーに合わせて撮ると、カードは「自己紹介」だった。カードの「正面」（`facingStop`）は軸の向きで決めていて、軸はその12°右のホログラムを向いていたため。つかんでいるあいだは、画面の中央の向き（`frameCentreDirection`、`roomCamera.ts` の純関数）で正面を決めるようにした。直したあとは、同じ構図で PC が正面になってカードが消えた（PC はカードを持たない）
- **◯**: 直径18px、白い2px の線に、黒の細い縁（明るい壁の前でも見えるように）。中央に固定するだけなので、毎フレーム位置を書く購読（`onView`）は外した

### miiiwa.com に繋がらない原因の調査

- **ユーザー**: 「なぜか miiiwa.com にアクセスできなくなりました。原因を調べてください」
- **症状**: `curl https://miiiwa.com` が `Could not resolve host`。ローカルのリゾルバでも 8.8.8.8 でも 1.1.1.1 でも、A レコードが空で返ってくる。サーバーが落ちたのではなく、**名前解決の段階で失敗**している
- **切り分けを外側から順に**:
  - ドメインの契約: whois で `Registry Expiry Date: 2027-09-08`、registrar は XServer。期限切れではない
  - 委任: `.com` のサーバー（`a.gtld-servers.net`）は `destiny`/`rommy.ns.cloudflare.com` を返す。委任は正しい
  - Cloudflare の権威サーバーに直接聞く: `miiiwa.com A` は **`NOERROR` で ANSWER 0**（SOA だけ）。ゾーンはあるのに、apex の A・AAAA・CNAME がどれも無い。`www` も無い。apex に残っているのは `google-site-verification` の TXT だけ

  - Vercel: プロジェクト `miwa-portfolio` に `miiiwa.com` が `verified: true` で付いたまま。最新の本番デプロイ（`bf2bef8`、PR #6）は `READY`。`get_domain_config` は `misconfigured: true`・`aValues: []` で、Vercel から見ても DNS が空
  - 配信そのもの: `miwa-portfolio.vercel.app` は 200。`--resolve miiiwa.com:443:76.76.21.21` で Vercel の IP に直接当てても 200（証明書も通る）。**Vercel 側は何も壊れていない**
- **結論**: Cloudflare の DNS から `miiiwa.com`（apex）を Vercel へ向けるレコードが消えた。コードやデプロイの変更が原因ではない。誰が・いつ消したかは Cloudflare の Audit Log でしか分からず、Cloudflare の MCP は未認可でこのセッションからは見られなかった
- **直し方**（Cloudflare のダッシュボード → DNS）: `A` / 名前 `@` / 値 `216.198.79.1`（Vercel の推奨の1番目。旧来の `76.76.21.21` でも動く）/ **プロキシは DNS only（灰色の雲）**。Vercel の証明書の発行と更新が Cloudflare のプロキシ越しだと邪魔されるので、DNS only にする
- **`www` は足さなくてよい**: Vercel のプロジェクトに `www.miiiwa.com` は登録されておらず、元から無かったと見られる
- **直した結果**: ユーザーが Cloudflare で `A @ 216.198.79.1`（DNS のみ・TTL 自動）を追加。直後に Cloudflare の権威サーバー・1.1.1.1・8.8.8.8 の3つとも `216.198.79.1` を返した。Vercel の `get_domain_config` も `misconfigured: false`。その IP へ HTTPS でつなぐと 200 で、証明書の検証も通った。**手元の Mac のリゾルバだけは、まだ「無い」と答えた**。「無い」という答えは SOA の negative TTL（1800秒）のあいだキャッシュされるので、最長30分は古い答えが残る
- **気づいたこと**: ゾーンに `bukka-now` の CNAME（`bukka-now.pages.dev` 向け、プロキシ済み）が増えていた。Pages のカスタムドメインの作業と apex が消えた時期が重なっているかもしれないが、Audit Log を見ていないので未確認
- **手元で古い答えを覚えていたのは Mac ではなくルーターだった**: Mac のキャッシュを消しても解決できなかった。Mac が問い合わせている先（`scutil --dns` の結果は `192.168.11.1`、家のルーター）に直接聞くと、SOA だけを残り TTL 1223秒で返した。ルーターが「無い」という答えを negative TTL（1800秒）のあいだ持っている。Mac の `dscacheutil -flushcache` では消えない

  - スマホは対象外。まず PC 側の UI を整える
- **段の順番を変えた**: 目的が「物の質」なので、ハード（Macintosh・メイン・縦置き・上の段）を先に1つずつ作り込み、仮想カーソル・視点・Windows の機能はそのあとにする

### モニターごとに寸法を持てるようにする（見た目は変えない）

- **何をしたか**: 3台が共有していた `MONITOR_Y`・`MONITOR_BEZEL`・`MONITOR_SCREEN`・`MONITOR_GLASS`・`MONITOR_FACE_Z` を外し、`MONITORS` の各台に高さ（`y`）・前枠（`bezel`）・画面（`screen`）・画面の下の前枠の余り（`chin`）を持たせた。ガラスと画面面は台ごとの関数（`monitorGlass`・`monitorFaceZ`）で導く。メインを大きくし、上の段・縦置きを足すための準備で、**値は3台とも元のまま**
- **なぜ関数にしたか**: ガラスの位置は前枠の奥行きから決まる。台ごとに定数を並べると、前枠を変えたときにガラスだけ取り残される（「同じ数を2箇所に持たない」）
