# 技術スタック (Tech Stack)

本プロジェクト（Miiiwa Portfolio）で使用されている主要な技術・ライブラリの一覧です。

## コア・フレームワーク
- **Next.js 16** (App Router) - Reactフレームワーク。本プロジェクトの基盤。`output: 'export'` による静的サイトとして書き出す構成のため、サーバー機能は使用していない。
- **React 19** - ユーザーインターフェース構築ライブラリ。
- **TypeScript** - 静的型付け言語。安全で堅牢なコードベースの維持に使用。
- **MDX**（`@next/mdx` + `remark-gfm`） - 制作実績の個別ページとノートの本文を書く形式。`src/content/` の `.mdx` を、ページから `import()` で読んでビルド時に HTML へ焼く（下の「読み物のページ」）。

## 3D表現・WebGL
- **Three.js** - ブラウザ上で3Dグラフィックスを描画するためのコアライブラリ。
- **@react-three/fiber** (R3F) - Three.jsをReactのコンポーネントとして宣言的に記述するためのラッパー。
- **@react-three/drei** - R3F用の便利なヘルパーライブラリ。今は `useCursor`（ホバー時のカーソル変更）だけを使う。`<Html>` は使わない（下の「HTML を3Dに置く」）。惑星の頃に使っていた `CameraControls` と `Stars` は外した。

## スタイリング・アニメーション
- **Tailwind CSS** (v4) - ユーティリティファーストのCSSフレームワーク。デザイントークンは `src/app/globals.css` の `:root` に集約。
- **Framer Motion** - React向けの高機能アニメーションライブラリ。セクションのフェードイン、詳細ページの開閉、モーダルの出現に使用。
- **Lucide React** / **React Icons** - SVGアイコンライブラリ。技術スタックのアイコンはローカル描画（外部CDNに依存しない）。
- **柔らかい環境光的な box-shadow（`shadow-sm`〜`shadow-2xl`）は採用しない方針。** カード・ヘッダー・詳細ページ（Products/Skills/Experience/Contact の内側のカード類も含む）は `border border-black/5` 系のボーダーだけで面の境界を示す。例外は2つ、どちらも「環境光」ではなく別の意味を持つ意図的な効果: (1) オレンジのCTAボタンの `shadow-[0_4px_0_...]`＋`active:shadow-none active:translate-y-1` は押し込み感を出す立体的な段差で、外すとボタンの物理的なフィードバックそのものが消える。(2) ステータスを示す小さいドットの `shadow-[0_0_8px/10px_...]` は発光表現で、面の下に落ちる影ではない。

## 主な特徴的な実装（アーキテクチャ）

トップページの3Dは、**ロケットを増改築したコロニーの中の、円い自分の部屋**（2026-10-01 に惑星から移行。要件・設計・各手順の実測は [room-migration.md](room-migration.md)、壊しやすい箇所は [scene-invariants.md](scene-invariants.md)）。惑星の頃の設計（球面の幾何、ボクセルの街、太陽、クロール）は [planet-archive.md](planet-archive.md) に記録として残してある。

- **すべてコードで手続き生成**: 外部の GLB も画像ファイルも使わない。家具は箱・円柱・球の組み合わせ、壁・床・丸窓の外・左のモニターの動画は canvas に描く（`scene/objects/roomTextures.ts`）。飾りの乱数は `scene/hash.ts` の `hash01` で決定的にしてある
- **ハイブリッド・レイアウト**: `<Canvas>` を背面に固定し、その上に通常の HTML のオーバーレイ（ヘッダー・カード・詳細シート）を重ねる。さらに、部屋の中の物として存在する HTML（PC の画面・ホログラムの文字）を、CSS の3D変換で canvas の後ろと手前に置く

- **家具の並び（右回り）**: 机（PC＋ホログラム）→ 展示棚（制作実績）→ 本棚（スキル）→ 丸窓とハンモック → 調査ボード（経歴）→ 通信端末（連絡先）→ 扉 → 作業台（3Dプリンタ）。PC の右隣からヘッダーのナビと同じ順なので、ナビで飛んでも位置関係が矛盾しない

### カメラ：中央に立って首を振る

- **姿勢は `RoomPose`**（首振り・見上げ・前に出る距離・目の高さ・画角・レンズ・横寄せ・縦のずらし、`scene/camera/roomCamera.ts`）。位置と向きは毎フレーム直接書き、カメラの「上」は常に world +Y
- **部屋は勝手に回らない。** ホイール・2本指・カードの送りで巡回の輪（`scene/room/tour.ts`）に沿って右へ首を振り、自由に見回すのは、PC ではマウス、スマホでは指のドラッグ（どちらも向けた向きのまま留まる）。**マウスはゲームの一人称のように照準を向ける**（2026-10-02）: 部屋をクリックするとマウスをつかみ（Pointer Lock API）、画面の中央に照準の◯が出て、動かした方を向く。クリックは照準を撃ち、つかんでいるあいだはカードも照準の向きで正面を決める。Esc か区画に寄るとカーソルが戻る。指のドラッグは「世界を掴む」、ホイールを下へ回すと右を向く。**止まっているあいだも、ゲームの一人称視点のような軽い揺れ**（`idleSway`、`scene/camera/cameraMotion.ts`）がある。2026-10-01 にユーザーの指示で、アイドルの自動の首振りから置き換えた
- **区画を選ぶと、その物の正面へ歩いて寄り、離れると中央へ後ろ歩きで戻る**（`RoomFlight`。最初のフレームに時間を加えない・着地で首振りの値を引き継ぐ、の2つの約束は惑星の飛行から）。飛行の形は `RoomMove` で、歩く形は `scene/camera/walkFlight.ts` の `planRoomMove`（加速・巡航1.5m/s・減速。PC は「歩く → 座る → 椅子ごと寄る」）。歩かない飛行（その場で回る・レンズの段）は今までどおり1本のイージング（`easedMove`）。行き先を決める effect は `Scene.tsx` に1つ
- **カードを避ける横寄せと、スマホのカードレールを避ける縦のずらしは、投影の中心をずらす**（`setViewOffset`）。カメラは動かさない
- **下を向くと目が前へ出る**（`headLean`）。首を支点に頭が傾く分で、自分の脚が胸の向こうに見える
- **W/A/S/D で部屋の中を歩き、Space で跳ぶ**（2026-10-02、`scene/camera/freeWalk.ts`）。見ている向きへ、飛行と同じ1.5m/s で歩く。壁と家具は `scene/room/floor.ts` が止める（体は半径22cm の円）。跳ぶ高さ45cm。**自由視点のときだけ**（寄っている・詳細ページ・飛行中は効かない）、入力欄に打っている文字と Ctrl/⌘/Alt 付きのキーは拾わない。立っている場所は `RoomPose` の `x`/`z` で、区画への寄り（中央から組んだ構図）へはそこから歩いて行き、離れるとそこへ歩いて戻る。ロゴ／HOME で中央へ

### レンズ：標準と魚眼

**`r = tan(θ/k)/tan(H/k)` の1本の式**（`scene/camera/fisheye.ts`）。k=1 が通常の遠近、k=2 が立体射影。標準⇄魚眼の飛行で k と画角を一緒に補間する。魚眼のあいだは立ち位置から6方向を立方体に描き、全画面の板のシェーダーで画素ごとに引く（`scene/LensRenderer.tsx`、`useFrame` の優先度1で描画を乗っ取る）。各面は MSAA をかけて描き、画面の解像度と画素比に合わせた大きさにする（2026-10-01、魚眼の輪郭が階段状になっていたのを直した）。マーカーの位置と大きさ、R3F のクリックの光線（`Scene.tsx` の `roomEvents`）も同じ式で求める。立体射影を選んだ理由（端の物の形が崩れない）と、画角を広げるだけの案を捨てた理由は room-migration.md の試作の節。

### HTML を3Dに置く（PC の画面とホログラム）

**本物の HTML を、CSS の3D変換で WebGL の画面の上の位置に合わせて置く**（`scene/camera/cssView.ts` の計算、`hub/room/RoomHtml.tsx` の層）。検索・スクリーンリーダー・文字の選択が効き、書き出した HTML にも文字が入る。カメラが毎フレーム姿勢を `viewChannel` に流し、層はその場で CSS を書く。

- **PC の画面は canvas の後ろ**に置き、canvas に穴（色とアルファ0、深度を書く板）を開けて見せる。手前の椅子やランプが画面を隠せる。**ホログラムは canvas の手前**に重ねる（透けないと成り立たない）
- **drei の `<Html>` を使わない理由**: 投影をずらしたカメラ（この部屋は常にずらしている）では位置がずれる。canvas 要素のスタイルも書き換える。詳細は scene-invariants.md
- **魚眼の段では HTML を出さない**（CSS は通常の遠近しか描けない）。穴も立方体のカメラに写さない（`scene/layers.ts`）

### PC（6か所目の停留所）

- **机の中央のモニターが PC の画面**（`hub/desk/DeskScreen.tsx`、1240×760px）。座ると（マーカー、ズームの段、`/#desk`）操作でき、ファイル（5セクション・ノート）とショートカット（GitHub・X・ターミナル）が並ぶ。**ファイルは PC の中のウィンドウで読み切る**（ユーザーの決定）。ウィンドウの中身は詳細シートと同じ部品（`Products`・`Skills`・`Experience`・`Contact`）
- **座っているあいだは canvas がポインタを通し、後ろの PC の画面が受ける**
- **PC はカードを持たない。** 正面のあいだはカード・点線・レールを出さず、カードの送りは PC を飛ばす
- 左のモニターは動画（今は手続きのループ）、右のモニターは天井近くの監視カメラの映像（下の「自分自身」）
- **机のキーボードとマウスは本物のように動く**（2026-10-22）。キーボードは HHKB Professional2（ロゴは「Miiiwa Professional3」）、マウスは ELECOM EX-G の S サイズ（ロゴは「Miiiwa」）。どちらも押すと沈んで録音の音が鳴る（Press & Click FREE、CC BY 4.0）。マウスは部品ごとに本当に割ってある（上の殻・本体・サイドボタン・DPI ボタン、幅0.6mm の割れ目）。**マウスは机の上を滑り、PC の画面のカーソルと一対一に対応する**: 読み手のポインタが PC の画面の上にあるときだけ、机のマウスがその位置へ動き、読み手のクリックとスクロールが机のマウスのボタンとホイールを動かす。机のマウスを長押しして滑らせると、画面に描いたカーソル（`hub/desk/ScreenCursor.tsx`）が動く。右手はマウスについて行く。不変条件と経緯は [scene-invariants.md](scene-invariants.md) の「描画」

### 自己紹介はホログラム

机の上のデバイスから光の円錐が伸び、その上の空中に自己紹介の文字が立って下から上へ流れる（`hub/about/Hologram.tsx`）。行/秒の自動再生（`hub/about/aboutScroll.ts`、一時停止で止まる）で、最後の行が上へ抜けたら中央へ戻る。途中で抜ける HOME もある。**スマホでは3Dの板が小さすぎて読めないので、同じ部品を画面の下部の平らな層に出している（仮）。** 惑星の頃のクロール（透明な canvas の後ろ、スクロールがカメラを引く帰り道）は外した。

### 照明

天井灯・デスクライトの入切と、ネオンの色の組（シアン×琥珀ほか）の切り替え。**状態は AppState に1か所**（`lights`）で、扉の脇のスイッチ板（3Dの物、`pointerClaim` で名乗る）とヘッダーの照明メニュー（`hub/LightMenu.tsx`）はどちらも `flipLight` を呼ぶだけ。**環境光の底は実測で決めた**（全部消しても、どの区画の被写体も点灯時の一番暗い被写体より暗くならない。試作の2倍）。太陽は無い。

### 自分自身

視点の人は部屋の主（Miiiwa）本人（ユーザーの決定）。体は視点のカメラの位置に立ち（`scene/room/self.ts` の関節、`scene/objects/Self.tsx`）、頭だけ three.js のレイヤーで視点のカメラから隠す。見える所は4つ: 右のモニターの監視カメラ（毎秒10回、`scene/objects/SecurityCamera.tsx`）、下を向いたときの体、座ったときのキーボードとマウスの上の手、丸窓への薄い映り込みの絵。

**見た目はキャラクターシート**（`reference/4/3.png`、Studio Wrong の見た目、2026-10-02）。寸法は `scene/room/figure.ts` がシートの正面の立ち姿の画素から測る（身長168cm・約5.8頭身）。**カメラの目の高さ（`EYE_HEIGHT`）も、座面の高さと椅子の背の位置も、ここから決まる。** 形はコードで組み（`Self.tsx`）、すべての部品は骨に乗った固い形で、骨は長さを変えない（脚も腕も2本の骨で、膝と肘で曲がる）。顔は頭の球に貼った絵（`objects/figureTextures.ts`。表情を絵の差し替えで増やせる）、眼鏡は形、髪は生え際の形に切った帽子と約60の束（1回の描画）。色はシートのパレットから取った。

**カメラが動くと体は歩き、PC では椅子に座る**（2026-10-02）。3つの純粋関数に分けてある:

- **歩き**（`scene/room/gait.ts`）: カメラの保っている姿勢の変化から、毎フレーム一歩の進み具合を求める。歩数は時間ではなく距離で数えるので、接地した足は滑らない。その場で回るのは足踏み。カメラの上下（`stepBob`）もここから
- **座る・椅子**（`scene/room/seat.ts`）: 座る度合い（`seatShare`）と椅子の位置（`chairPlacement`）を、カメラの保っている姿勢だけから求める。椅子は普段は通り道の脇にあり、近づくと背後へ回り、腰の下に入り、椅子ごと机へ寄る
- **関節**（`scene/room/self.ts`）: 姿勢・歩き・座る度合いから全身の関節を出す。脚は2本の骨で、膝は前へ曲がる

**ホログラムには自分が映る**（2026-10-02 ユーザー。`scene/objects/HologramSelf.tsx`）。同じ人物（`FigureModel`）を4分の1の大きさで、光の材質（縁が明るく、走査線が流れる）で描き、装置の上の光の中でゆっくり回る。読み手が歩けば歩き、見上げれば見上げる。右のモニターが装置の前にあるので、装置に立たせず、前の線画と同じ高さに浮かべた。自己紹介を映しているあいだは消える。

**姿が見える所は、モニター（監視カメラ）と鏡**（2026-10-02 ユーザー）。鏡は経歴・活動の看板の右上のカーブミラー（`scene/room/mirror.ts` が位置、`scene/objects/CurveMirror.tsx` が描画）で、本物の反射（鏡の前から描いた立方体を、反射の向きで引く）。

カメラの制御（`Scene.tsx` の `applyPose`）が歩きを求めて `viewChannel` の `publishBody` で配り、体（`Self.tsx`）と椅子（`RoomScene.tsx` の `Chair`）がそれを読む。どちらもカメラから何も教わらずに、飛行・ドラッグ・座る動きに付いて行く。この先の「操作が無いときに自分で歩き回る」「ハンモックで本を読む」は、まだ作っていない（ユーザーの次の要望。`docs/room-migration.md` の要件）

### エリアのマーカーと点線

マーカーは WebGL のスプライト（深度バッファに乗るので家具に隠れる）、カードからマーカーへの点線は DOM の SVG（常に最前面の平面）。両者の受け渡しは購読チャンネル（`scene/camera/markerScreen.ts`）経由で、React state を通さない（毎フレームの再レンダーを避けるため）。

- **マーカーは円盤ではなく水色の稲妻**（`scene/markerBolt.ts` の `BOLT_PATH`）。輪郭・到達距離・**寸法比**（`MARKER_CLEARANCE` / `MARKER_GLYPH_FILL` / `MARKER_GLYPH_RIM` / `MARKER_GLOW_FILL`）・火花・色をここに集めてあり、three.js も canvas も DOM も含まない純粋モジュールなので、3つの消費側（WebGL のスプライト／SVG の点線／カード隅のドット）が同じ形と同じ色を読む。**カメラ側に置くのは射影とレンズの拡大率だけ**（`scene/camera/roomCamera.ts` の `projectToScreen()` / `pixelsPerUnitAt()`）——寸法比は 2026-09-11 のファイル構成レビューまでカメラ側にあり、テクスチャを描く側と点線が縁を測る側が別モジュールの数を見る形になっていた（`SectionMarkers.tsx` が同じ「マーカーの見た目」のために2つの import を持っていたのがその痕跡）。
  - **座標系は「x右・y下」で `y ∈ [-1, 1]`。** canvas 2D も画面 px も y は下向きなので、テクスチャを描く側と点線に答える側で符号を変えずに済む。**縦が ±1 に届くことがスプライトの sizing の前提**——マーカーの scale は「グリフが `halfHeight` px に届くワールド scale」として逆算するので、輪郭が ±1 に届いていないと全マーカーが黙って小さくなる。
  - **点線の切り詰めは `markerClearance()` を通す。`halfHeight` をそのまま引かない。** 稲妻は縦長で先端が軸から外れているため、インクの縁までの距離は方向ごとに違う（真上 0.61・真横 0.45・真下 0.60 × halfHeight）。中心からレイを飛ばして輪郭との交点を取る厳密解で、**内接楕円は先端がはみ出すので安全ですらなく**（(0.30/0.52)² + 1 = 1.33）、**凸包の支持関数は安全だが真下で1.67倍**と緩い。どちらも「隙間が方向によって呼吸する」を招く。
  - **この輪郭は中心について星形**（20000方向中19999で前方交点はちょうど1つ）。だから「どこまで届くか」に単一の答えがある。実装が max を取っているのは星形でなくなったときの保険で、いま効いている条件ではない。
  - **`MarkerScreenPoint` が渡すのは `radius` ではなく `halfHeight`。** 円でないものを半径と呼ぶと「どの方向でも同じはず」と読まれる。
  - **`MARKER_GLYPH_FILL = 0.34`（旧 `MARKER_DOT_FILL` 0.37）はグリフの実体、`MARKER_GLOW_FILL = 0.46` はグローの届く範囲で、点線はグローを数えない。** クアッドの端は 0.5 なので余白 0.04 を残してある（端まで届かせるとクランプで四角く切られる）。
  - **canvas に描くときは `lineJoin = "round"` が必須。** 既定の miter は稲妻の鋭角で `MARKER_GLYPH_FILL` の外へ棘を飛ばし、縦の到達点＝sizing の前提を壊す。円には角が無かったので存在しなかった罠。グローは `ctx.shadowBlur` で同じパスを3回 fill する（ラジアルグラデーションだと丸くない形の周りに丸い光の玉が付く）。
  - **火花（`boltFlicker()`）は正面のマーカーだけ、サイズではなく明るさに掛ける。** サイズは点線が一定距離で追いかけている数なので、そこに掛けると火花のたびに点線の先端が痙攣する。`toneMapped={false}` なので明るさ倍率は各チャンネル1で頭打ちになり、水色が一瞬白く飛ぶ。時刻は `sceneClock` 経由なので停止ボタンで止まる。
- **点線も規則的なジグザグをやめて稲妻の折れ線になった**（`hub/card/lightningPath.ts`、純粋関数）。乱数は `scene/hash.ts` の `hash01()`。
  - **座標系は `(along, lift)`**——線に沿った距離と、軸からの横ズレ。画面座標への変換は `CardLeaderLine` の仕事なので、形は DOM 抜きでテストでき、線の向きにも依存しない。
  - **端の連続性は包絡線（`envelope()`）が担保する。端をピン留めする特別扱いを足さない。** `lift` に `min(along - from, to - along) / RAMP` を掛けると、頂点が生まれる瞬間はちょうど `to - along = 0` なので**必ず軸上で生まれて育つ**。終点の `lift = 0` も自動的に落ちる。旧ジグザグの「余りの山が余白に応じて育つ」特殊ケースは、これに置き換わって削除済み。
  - **折れ方は左右への切り返し。「平均回帰する歩行」にしてはいけない。** 凸結合は中央へ引っ張るので、定常のばらつきが刻みに対して小さくなり**ゆるく波打つ線**になる（一度そう実装して、ヘッドレスのスクショで判明した）。`RUN_CHANCE` で時々同じ側を続けるのが鋸歯にしないための味付け。
  - **引き直しの拍は `strikeIndex()` から取る。独立した周期定数を作らない。** `boltFlicker` と `FLICKER_PERIOD` を共有しているので、「マーカーが光る瞬間に線も引き直される」が定義上ずれない。値は `markerScreen` の購読チャンネルに `strike` として載る——`CardLeaderLine` はキャンバス外の DOM で `sceneClock` を自分では読めないため。停止ボタンで時計が止まれば線も固まる。
  - **枝（フォーク）は最大3本、`FORK_SPACING` で線全体に散らす。** 分岐判定は頂点ごとに独立なので、間隔を空けないと枠が手前で埋まり、**残りが素の線**になる。張り出しは `FORK_REACH` という「予算」で持つ（節ごとの振れ幅を積む書き方だと、実際の到達距離が誰も決めていない数になる）。
  - **DOM は `<path>` 3本**: グロー（幹と同じ `d`、太く薄い）／枝（複数サブパスを1要素に、細く薄い）／幹。従来どおり React state は通さず属性を直書きする。
- **色は `markerBolt.ts` の4定数だけ**: `MARKER_IDLE_INK`（`#a6dbf7`）・`MARKER_FACING_INK`（`#7fe8ff`）・`MARKER_TRAIL_INK`（`rgba(58,160,208,0.75)`、線とカード隅のドット）・`MARKER_TRAIL_GLOW`（`rgba(126,212,245,0.3)`）。マーカーのテクスチャは白で描いて `SpriteMaterial.color` の乗算でティントするので、グローも縁取りも一緒に色が乗る。**線だけ濃いのは白いカードの上を通るから**——`#a6dbf7` は白地でほぼ消える。カード側は Tailwind の任意値クラスではなくインラインスタイルで受ける（クラス走査はリテラルしか読めない）。

- **マーカーと点線は「招待状」で、フォーカスした時点で役目が終わる**: エリアにズームすると `activeSection` が立ち、**全マーカーが半径0**になり、点線とカード側のアンカードットも消える。スポットライトのドットだけ「イージングしない」特例があるが、それは**入場方向にだけ**適用する。
- **カードは重ね（スタック）で、ホバー中のホイールでエリアを送れる**（`card/SectionCard.tsx` / `hub/card/cardWheel.ts`）。送り先は部屋の順で、PC を飛ばす（`adjacentSection()`、`scene/room/tour.ts`）。ホイールは React の `onWheel` ではなく素の `addEventListener` で取る（`preventDefault`/`stopPropagation` が要るため）。
- **カードの送りは2つのゲートで守られていて、役割が違う。片方を厚くしてもう片方を薄くする、という調整はできない。**
  - **ジェスチャの区切り（`hub/card/cardWheel.ts`、純粋関数）** — 「1ジェスチャ＝1枚」。しきい値 `WHEEL_THRESHOLD = 80` を越えた瞬間にロックし、`GESTURE_GAP_MS = 220` の静止で解ける。**静止だけを解除条件にしてはいけない**——トラックパッドの慣性テールは1〜2秒 wheel を吐き続けるので、テールに重なった2回目のフリックが丸ごと飲まれる（＝スクロールが効いたり効かなかったりする、の正体）。テールは単調に減衰するという性質を使い、**山の半分を下回ってから2.5倍以上に跳ね上がった**イベントも新しいジェスチャとして扱う（`REARM_DECAY_SHARE` / `REARM_RISE`）。フリック自身の立ち上がりで誤爆しないのは、上昇中は「直前のイベント＝山」で減衰の条件が成立しないため。
  - **到着ゲート（`card/SectionCard.tsx`）** — 「まだ出ていないカードの、その次」へは進めない。ステップは**変更ではなく要求**で、`section` が返ってくるのはカメラが実際に振れたあと（damp λ=5 で約0.13秒）。`pendingSince` を立て、`section` が変わったことだけを到着の合図として降ろし、さらに登場スプリングが収まる `CARD_SETTLE_MS = 160`（ζ≈1.11・遅い極の時定数64ms）を待つ。**この2つで最短約0.3秒＝毎秒3枚。** `STEP_TIMEOUT_MS = 1000` は要求が飛行などで届かなかったときにカードが永久に固まらないための保険であって、通常経路では踏まない。
  - **ゲートに弾かれたジェスチャも `locked` のままにする。** 拒否のたびに accumulator を生かしておくと、ゲートが開いた瞬間にテールに溜まった移動量が発火して「読み手が頼んでいない1枚」になる。次の新しいジェスチャ（静止 or 再上昇）で必ず通る。
  - **`deltaY` は `deltaMode` を見て px に正規化する**（`wheelPixels()`）。Chrome はマウス1ノッチを100px、Firefox は同じ1ノッチを3行で寄越すので、正規化しないとしきい値80に対して**27ノッチ必要＝実質死んだコントロール**になる。
- **点線の起点は、作り直される要素の中に置かない。** カードは `AnimatePresence` で切り替わりのたびに作り直されるため、アンカーの点は**カードの中ではなくスタックのコンテナ**に置く——退場側の ref コールバックが `null` で後から呼ばれて `anchorRef.current` が空になると、線が最後の位置で凍る。
- **マーカーの位置は `layout.ts` の `markerPoint()`**（被写体の上、少し中央寄り。家具に刺さらないように）。PC にもマーカーがある（押すと座る）
- **マーカーの大きさは world 単位ではなく画面 px で決める。** そのスプライトの位置での拡大率（通常の遠近なら焦点距離÷奥行き、魚眼ならレンズの拡大率、`pixelsPerUnitAt()`）から、グリフが指定した px の縦半分に届くワールド scale を毎フレーム逆算する
- **カメラの `useFrame` はマーカーより先に走る（優先度 -1）。** 惑星の頃は `camera-controls` が行列を張り直さない問題を `updateMatrixWorld()` で防いでいた。部屋ではカメラの処理の順番そのものが逆になっていて、点線の先が1フレーム遅れていた（手順3で直した）
### ジオラマの時計

自分から動くもの（視点の揺れ・マーカーの脈動・左のモニターの動画・ホログラムの仮の多面体の回転・ホログラムの文字の自動再生）は、レンダラの時刻ではなく `scene/sceneClock.ts` を読む。ヘッダーの停止ボタンはこの時計を凍らせるだけで、全部が同じフレームに止まる。停止していた時間は加算されるのではなく**割り引かれる**ので、再生は止めた瞬間の続きから始まる。停止中もカメラは手で回せる——首振りの減衰には実 delta を渡し、揺れだけこの時計を通しているため。

**この時計はレンダラの時刻が単調でないことを前提に組んである。** `frameloop` を `"demand"`↔`"always"` で切り替えると、R3F の `setFrameloop` が `clock.stop(); clock.elapsedTime = 0; clock.start(); clock.elapsedTime = 0` を実行する（`events-*.esm.js`）——詳細ページを開くたび・閉じるたびに**レンダラの時刻が0から数え直しになる**。`sceneClock` は内部に `restarts`（巻き戻り幅の累計）を持ち、渡された `elapsed` が前回より小さければその差を積んで補正する。これが無いと、時刻の関数で位置が決まるもの（マーカーの脈動と `strikeIndex`、動画）が**閉じた瞬間に一斉にワープする**——しかも `Hub.tsx` は progress がわずかでも立てば `setCovered(false)` を投げるので、スペーサが透けて部屋が見えている状態で起きる。`setPaused` も同じ補正を通す（`frozenAt` と `skipped` が `time()` の答えと同じ座標系に乗る必要がある）。**`frameloop` の切り替え自体は残す**——省電力のためのもので、直すべきはこちら側。

### 毎フレームの値は React state に載せない

**`<Canvas>` より上のコンテキストが変わると、three.js のツリー全体が React に再調停される。** R3F 9 の `CanvasImpl` の setup effect には**依存配列が無く**、再レンダーのたびに `configure()` と `root.render(children)` が走る——部屋の家具・体・照明が毎回そこを通る。

- **`React.memo` では止められない。** `its-fine` の `useContextBridge`（R3F がコンテキストをリコンサイラ境界の向こうへ運ぶ仕組み）は `CanvasImpl` のレンダー中に上位の全コンテキストを `use()` で購読するので、props が変わらなくても Canvas は再レンダーする。しかも memo すると今度は `CameraController` が `activeSection` の変化を受け取れなくなる——Bridge は `root.render` 経由でしか新しい値を運ばないため。**打てる手は「Canvas より上のコンテキストが変わる回数を減らす」しかない。**
- そのため、毎フレームまたは頻繁に変わる値は**購読チャンネル**（プレーンなモジュール＋リスナーの `Set`）で運ぶ。現在4つ: `scene/camera/viewChannel.ts`（カメラの姿勢と画面の大きさ。HTML を3Dに置く層とレンズの描画が読む）、`scene/camera/markerScreen.ts`（マーカーの画面座標）、`state/facingChannel.ts`（正面の停留所）、`scene/deskPointer.ts`（机のマウスの位置と PC の画面のカーソル。カーソルの絵と座った右手が読む）。**照明の状態は Context に置いている**——切り替えは読み手の操作でしか起きず、そのたびの再調停は問題にならない。
- **`facing` の読み手は3種類に分かれる**: `SectionCard` は `useSyncExternalStore` で購読（表示するので再レンダーが要る）、`SectionMarkers` は `useFrame` の中で `facingNow()` を読む（描くだけなので再レンダー不要）、`Hub` はハンドラが発火した時点で読む（`cardSection()`）。`AppStateContext` に置いていた頃は1ラップに5回、シーン全体の再調停を起こしていた。
- `AppStateContext` の value は `useMemo` で包んである。

### その他

- **省電力**: 詳細ページがキャンバスを覆っている間は `frameloop="demand"` に切り替え、毎秒1回だけ描画する。**切り替えはレンダラの時計をリセットする**ので、`sceneClock` 側の補正とセット（「ジオラマの時計」参照）。
- **URL**: 開いているセクションをハッシュ（`#products` 等）に反映し、戻るボタンとリンク共有に対応。**PC に座っているあいだは `#desk`**（シートを持たないので、区画とは別の規則。`state/sectionUrl.ts` の `hashForState`）。セクションの詳細シートはクライアント描画だが、PC の画面のウィンドウとホログラムの文は部屋の中の HTML として書き出される。
- **経歴から制作実績へ（`detail/Sheet.tsx`）。** 経歴のうち `project`（実績の slug）を持つ項目はカード全体がボタンになり、押すと制作実績に切り替わって、その実績のモーダルが最初から開く。切り替えはヘッダーのナビがシートを開いたまま行うのと同じ `setActiveSection("products")` で、URL も `#products` に進むので、ブラウザの戻るで経歴に帰れる。**「どの実績を開くか」は `AppStateContext` ではなく `Sheet` の state に持つ**——Context に置くと、変わるたびに three.js のツリー全体が再調停される（「毎フレームの値は React state に載せない」）うえ、シーンには関係の無い値だから。`Products` はそれを `useState` の初期値として**マウント時に一度だけ**読み、以後モーダルは読み手のもの（閉じたら戻ってこない）。**依頼は制作実績以外のセクションへ移った瞬間に捨てる**。effect ではなく、前回の `activeSection` を state に持ってレンダー中に比べる形（React の「前回のレンダーの情報を保存する」）——effect で消すと、このプロジェクトの lint（`react-hooks/set-state-in-effect`）に掛かり、描画も1回余分に走る。捨てないと、経歴で押した直後（`Products` がマウントされる前、シートの切り替えアニメーションの0.3秒）に別のセクションへ移ったとき、あとで普通に制作実績を開いた瞬間に関係の無いモーダルが開く
- **制作実績の Code／Play は `next/link` ではなく素の `<a>`（`detail/products/ProjectLinks.tsx`）。** 実績のリンク先は、他ドメインか、同じサイトに同居させた過去バージョン（`/archive/v0`・`/archive/v1`、[structure.md](structure.md) の「`public/archive/`」）のどちらかで、**このアプリのルートは1つも無い**。`<Link>` は本番でビューポートに入ったリンクを自分のルートとして先読みするので、`/archive/v1` を指すと**実績を開いただけで v1 のルートツリー・CSS・フォントの計6件を取りに行く**（本番ビルドで実測。`<a>` にして0件）。`target="_blank"` なのでクリック時のクライアント遷移は元々起きず、`<Link>` を使う利点が無い。
